# Правила для агентов (Claude Code, Codex)

Единый источник правил разработки в этом репозитории. Его читают все агенты:
Codex — напрямую, Claude Code — через импорт в `CLAUDE.md`. Правила меняются
только здесь. Владелец проекта — единственный человек в процессе. Он ставит
задачи и даёт аппрув на мерж.

## Состояние репозитория

- `main` = прод. Любой push в `main` запускает GitHub Actions: проверки, затем
  деплой на прод-хост с миграциями на живой БД. Push только документов тоже
  деплоит.
- Долгоживущих веток, кроме `main`, нет. Каждая ветка — это одна задача в работе.
- Основной checkout (`budget_bot/`) стоит на `main` и чистый. Агенты в нём не
  работают, кроме короткой задачи, о которой владелец попросил явно.

## Задача: ветка + worktree

1. Одна задача — одна ветка — один worktree. Ветка называется
   `<агент>/<кратко-о-задаче>`, например `claude/income-tax-check` или
   `codex/fx-rounding`. Префикс показывает, чья ветка.
2. Ветка создаётся от свежего `origin/main` (`git fetch` перед стартом).
   Worktree — в `.worktrees/<имя>` или там, где его создаёт инструмент агента.
3. Перед стартом посмотрите `git worktree list` и `git branch`. Если чужая
   активная ветка трогает те же файлы или ту же область (таблица, SQL-функция,
   роутер, экран), остановитесь и спросите владельца. Два агента не правят одни
   файлы параллельно.
4. Коммит после каждого законченного и проверенного шага: один логический шаг —
   один коммит. Сообщение на английском, в повелительном наклонении, о том, что
   и зачем поменялось. Коммитить можно без отдельного разрешения.

## Мерж и деплой — только после аппрува владельца

1. Задача готова, когда проходят проверки (раздел ниже), написан отчёт в
   `docs/` и все шаги закоммичены.
2. Агент кратко сообщает владельцу, что меняется для пользователя, есть ли
   миграции БД и риски, и **ждёт явного «да»**. Аппрув действует для одного
   мержа и не переносится на следующие.
3. После аппрува: `git fetch`, rebase или merge ветки на `origin/main`, повторные
   проверки, затем `git push origin HEAD:main`. Без `--force`.
4. Агент дожидается результата CI/деплоя и проверяет, что прод поднялся.
   Запись о деплое добавляется в отчёт задачи и уходит со следующим push.
5. После мержа удалить worktree и ветку (локально и на GitHub, если пушилась).

Без аппрува нельзя: push в `main`, `--force`, `reset --hard`, `checkout .`,
`clean`, удаление чужих веток и worktree. Перед любой из этих операций —
`git status`.

## Проверки

- Backend: `./venv/bin/ruff check backend storage`.
- Frontend (в `frontend/`): `npm run typecheck`, `npm run lint`.
- Схема и SQL: полный набор — в `.github/workflows/budget_bot_ci_cd.yml`
  (схема с нуля, откат миграций, SQL- и API-тесты, Playwright smoke). Изменения
  БД проверяются локально тем же способом, что и в CI.
- Нетривиальная денежная или security-логика оставляет после себя один
  запускаемый тест.

## Документация

Перед работой в области прочитайте соответствующий документ:

- `BUSINESS_LOGIC.md` — доменная модель и четыре слоя; правила в `backend/`, `storage/`.
- `DATA_MODEL.dbml` — текущая схема PostgreSQL; таблицы и SQL-функции в `infra/db/`.
- `DEVELOPMENT_GUIDELINES.md` — правила кода, выведенные из прошлых багов, и
  чеклист перед коммитом. Обязателен для любой нетривиальной правки.
- `FRONTEND_CHECKLIST.md` — что из бэкенда ещё не сделано во фронтенде.
- `docs/*.md` без даты — справочники (крипто-политика, Tinkoff, safe area, бэкапы).

Два вида документов, и нужны оба:

- **Отчёт** `docs/YYYY-MM-DD-кратко.md` — после любой задачи, которая поменяла
  поведение системы. В нём: цель; последовательность, которая сработала
  (без тупиков); что нашли при диагностике; команды отката; открытые вопросы.
- **Справочник** (файлы без даты) — обновляется, когда меняется устройство
  системы или процесс. Новое правило из бага дописывается в
  `DEVELOPMENT_GUIDELINES.md`.

## Безопасность — в первую очередь

- Если есть выбор, берётся безопасный вариант. Отступить от него можно только
  по явному решению владельца.
- Вынужденный компромисс (ослабленная проверка, широкий доступ, временный
  секрет) записывается в отчёт задачи в раздел «Известные уязвимости /
  осознанные риски». Тихих компромиссов не бывает.
- Секреты не попадают в git, в чат, в аргументы команд и в правила разрешений.
  `.env*` игнорируются, кроме `.env.example`.
- Прод-БД — только чтение (`agent_readonly` / readonly MCP). Любая запись в
  прод, ручной SQL на проде и операции на прод-хосте — только с аппрувом
  владельца на конкретное действие.

## Личные данные и рабочие артефакты

- Реальные финансовые данные владельца (выписки, крипто-история, дампы БД) в
  репозитории не хранятся, даже в игнорируемых папках.
- Архив лежит рядом: `../budget_bot_archive/` (см. его `README.md`). Артефакты
  задачи (дампы, выгрузки, отчёты сверки) складываются в
  `../budget_bot_archive/<дата>-<задача>/`, не в репозиторий.
- Тесты и CI используют только синтетические фикстуры.
