# Правила для агентов (Claude Code, Codex)

Единый источник правил разработки в этом репозитории. Его читают все агенты:
Codex — напрямую, Claude Code — через импорт в `CLAUDE.md`. Правила меняются
только здесь. Владелец проекта — единственный человек в процессе. Он ставит
задачи и даёт аппрув на мерж.

## Состояние репозитория

- `main` = прод. Любой push в `main` запускает GitHub Actions: проверки, затем
  деплой на прод-хост с миграциями на живой БД. Push только документов тоже
  деплоит.
- Долгоживущих веток, кроме `main`, нет. Каждая ветка — это одна задача в работе.
- Основной checkout (`budget_bot/`) стоит на `main` и чистый. Агенты в нём не
  работают, кроме короткой задачи, о которой владелец попросил явно.

## Задача: ветка + worktree

1. Одна задача — одна ветка — один worktree. Ветка называется
   `<агент>/<кратко-о-задаче>`, например `claude/income-tax-check` или
   `codex/fx-rounding`. Префикс показывает, чья ветка.
2. Ветка создаётся от свежего `origin/main` (`git fetch` перед стартом).
   Worktree — в `.worktrees/<имя>` или там, где его создаёт инструмент агента.
3. Перед стартом посмотрите `git worktree list` и `git branch`. Если чужая
   активная ветка трогает те же файлы или ту же область (таблица, SQL-функция,
   роутер, экран), остановитесь и спросите владельца. Два агента не правят одни
   файлы параллельно.
4. Коммит после каждого законченного и проверенного шага: один логический шаг —
   один коммит. Сообщение на английском, в повелительном наклонении, о том, что
   и зачем поменялось. Коммитить можно без отдельного разрешения.

## Процесс доработки

### Уровень задачи

Уровень предлагает сессия-планировщик, владелец подтверждает его вместе с планом.

| Уровень | Когда | Этапы |
|---|---|---|
| **S** | текст, стиль, мелкий баг без денег, БД и безопасности | правка + тест + проверки → аппрув мержа |
| **M** | обычная фича или фикс | план → аппрув плана → реализация → финальное ревью → аппрув мержа |
| **L** | деньги, схема БД/миграции, безопасность, больше ~3 областей | план → ревью плана → вопросы владельцу → аппрув плана → реализация → финальное ревью → аппрув мержа |

Задача, которая меняет интерфейс, на уровнях M и L дополнительно проходит
UI/UX-трек (см. ниже).

### План — один файл

План — это начало отчёта задачи `docs/YYYY-MM-DD-кратко.md`. По ходу работы тот
же файл дополняется до отчёта. Ревьюеры получают только этот файл и
репозиторий, без переписки, поэтому всё нужное должно быть в нём:

- цель и что не входит в задачу;
- **критерии приёмки** — пронумерованные, проверяемые;
- **тесты**: какой тест доказывает какой критерий;
- затронутые области, миграции, откат;
- для UI — экраны, состояния, переиспользуемые компоненты;
- открытые вопросы владельцу.

### Этапы

1. **План.** Сессия-автор читает документацию области и пишет план.
2. **Ревью плана (L).** Свежая сессия без контекста чата проверяет план по
   чек-листу:
   - соответствие `BUSINESS_LOGIC.md`, `DATA_MODEL.dbml`, `DEVELOPMENT_GUIDELINES.md`;
   - граничные случаи, безопасность, откат;
   - **есть ли вариант проще**.

   Замечания дописываются в план разделом «Ревью плана» с пометкой
   «исправить» или «вопрос владельцу». Один раунд; второй — только если план
   переписан существенно.
3. **Аппрув плана.** Владелец отвечает на вопросы и подтверждает финальный план.
4. **Реализация.** Для денежной и security-логики сначала пишется падающий
   тест, потом код. Каждый критерий приёмки закрыт тестом. Проверки делаются
   инструментами (линтеры, тайпчек, тесты, `/code-review`, `/security-review`),
   а не на глаз.
5. **Финальное ревью.** Свежая сессия получает план и дифф
   `origin/main...<ветка>`:
   - запускает проверки;
   - прогоняет `/code-review` и для чувствительных мест `/security-review`;
   - сверяет каждый критерий приёмки с кодом и тестом.

   Замечания дописываются в файл разделом «Финальное ревью». Автор их
   исправляет, ревьюер перепроверяет только исправления.
6. **Аппрув мержа** (раздел ниже).

Владелец участвует только в шагах 3 и 6. Остальное идёт без него. Ревьюеров
запускает сессия-автор в Claude Code и получает их результат обратно. Если
автор — Codex, ревью-сессии запускает владелец или Claude.

### UI/UX-трек

Нужен для любой задачи, которая меняет интерфейс. Основа — дизайн-справочник
`docs/design-guide.md` (пока его нет — см. бэклог):

- токены, темы, паттерны (шторки, строки позиций, пикеры, формы сумм);
- мобильная ширина 375–430, safe area Telegram;
- тон текстов.

Шаги трека:

1. **Дизайн в плане.** Дизайн-сессия дополняет план:
   - раскладка экрана;
   - все состояния (пусто, загрузка, ошибка, длинные суммы и названия);
   - какие существующие компоненты переиспользовать.
2. **Дизайн-ревью после реализации** — после автора, до финального ревью, не
   параллельно с ним. Дизайн-сессия запускает фронтенд в браузере на 390px в
   светлой и тёмной теме, снимает скриншоты до и после и проверяет:
   - соответствие справочнику;
   - доступность;
   - тексты.

   Визуальные правки (CSS, разметку, тексты) она **делает сама**. Замечания по
   логике возвращает автору.
3. **UI-тесты** — по слоям, от дешёвого к дорогому:
   - юнит-тесты логики отображения (`frontend/tests`);
   - Playwright e2e по критериям приёмки;
   - визуальные снимки изменённых экранов (390px, обе темы). Эталоны
     обновляются только вместе с осознанной правкой дизайна;
   - автопроверка доступности (axe) в тех же тестах.

UI-тесты, скриншоты и визуальные эталоны делаются **только на синтетических
данных** из тестового сида. Dev-база, скопированная с прода, для них не
используется, иначе реальные балансы попадут в git.

## Мерж и деплой — только после аппрува владельца

1. Задача готова, когда проходят проверки (раздел ниже), написан отчёт в
   `docs/` и все шаги закоммичены.
2. Агент кратко сообщает владельцу, что меняется для пользователя, есть ли
   миграции БД и риски, и **ждёт явного «да»**. Аппрув действует для одного
   мержа и не переносится на следующие.
3. После аппрува: `git fetch`, rebase или merge ветки на `origin/main`, повторные
   проверки, затем `git push origin HEAD:main`. Без `--force`.
4. Агент дожидается результата CI/деплоя и проверяет, что прод поднялся.
   Запись о деплое добавляется в отчёт задачи и уходит со следующим push.
5. После мержа удалить worktree и ветку (локально и на GitHub, если пушилась).

Без аппрува нельзя: push в `main`, `--force`, `reset --hard`, `checkout .`,
`clean`, удаление чужих веток и worktree. Перед любой из этих операций —
`git status`.

## Проверки

**Готово = `scripts/check.sh` зелёный.** Скрипт локально повторяет job
`verify` из `.github/workflows/budget_bot_ci_cd.yml` теми же командами и в том
же порядке: frontend build/lint, ruff, юнит-тесты, `py_compile`, `bash -n`,
прямые hex-цвета в `styles.css`, схема с нуля, SQL- и API-тесты,
`docker compose config`. БД —
одноразовый контейнер `postgres:17` (нужен Docker), dev-база и прод не
трогаются. В конце — итог по шагам, код выхода ≠ 0 при любой ошибке.

- `scripts/check.sh --fast` — ruff, typecheck, lint, hex-цвета, юниты (секунды).
  Его же запускает git pre-commit хук. Установка один раз на репозиторий
  (действует во всех worktree): `git config core.hooksPath scripts/git-hooks`.
  `--no-verify` — только осознанно, с причиной в отчёте задачи.
- Новый hex-цвет вне `:root` / `[data-theme=…]` → `var(--…)`. Старые записаны в
  `scripts/css-hex-baseline.txt`; исправили старые — обновите baseline:
  `scripts/check_css_hex.py --update-baseline`.
- Меняете CI — меняйте `scripts/check.sh` тем же коммитом.
- Нетривиальная денежная или security-логика оставляет после себя один
  запускаемый тест.

## Документация

Перед работой в области прочитайте соответствующий документ:

- `BUSINESS_LOGIC.md` — доменная модель и четыре слоя; правила в `backend/`, `storage/`.
- `DATA_MODEL.dbml` — текущая схема PostgreSQL; таблицы и SQL-функции в `infra/db/`.
- `DEVELOPMENT_GUIDELINES.md` — правила кода, выведенные из прошлых багов, и
  чеклист перед коммитом. Обязателен для любой нетривиальной правки.
- `FRONTEND_CHECKLIST.md` — что из бэкенда ещё не сделано во фронтенде.
- `docs/*.md` без даты — справочники (крипто-политика, Tinkoff, safe area, бэкапы).

Два вида документов, и нужны оба:

- **Отчёт** `docs/YYYY-MM-DD-кратко.md` — после любой задачи, которая поменяла
  поведение системы. В нём: цель; последовательность, которая сработала
  (без тупиков); что нашли при диагностике; команды отката; открытые вопросы.
- **Справочник** (файлы без даты) — обновляется, когда меняется устройство
  системы или процесс. Новое правило из бага дописывается в
  `DEVELOPMENT_GUIDELINES.md`.

## Безопасность — в первую очередь

- Если есть выбор, берётся безопасный вариант. Отступить от него можно только
  по явному решению владельца.
- Вынужденный компромисс (ослабленная проверка, широкий доступ, временный
  секрет) записывается в отчёт задачи в раздел «Известные уязвимости /
  осознанные риски». Тихих компромиссов не бывает.
- Секреты не попадают в git, в чат, в аргументы команд и в правила разрешений.
  `.env*` игнорируются, кроме `.env.example`.
- Прод-БД — только чтение (`agent_readonly` / readonly MCP). Любая запись в
  прод, ручной SQL на проде и операции на прод-хосте — только с аппрувом
  владельца на конкретное действие.

## Личные данные и рабочие артефакты

- Реальные финансовые данные владельца (выписки, крипто-история, дампы БД) в
  репозитории не хранятся, даже в игнорируемых папках.
- Архив лежит рядом: `../budget_bot_archive/` (см. его `README.md`). Артефакты
  задачи (дампы, выгрузки, отчёты сверки) складываются в
  `../budget_bot_archive/<дата>-<задача>/`, не в репозиторий.
- Тесты и CI используют только синтетические фикстуры.
