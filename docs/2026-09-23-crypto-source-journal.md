# Общий журнал исходных криптособытий

23.09.2026. Продолжение пункта 2 чеклиста; личная история ещё не импортирована.

## Что готово

Новый `POST /api/v1/crypto/source-events` проводит исходное событие через
существующие функции учёта в одной транзакции. Событие содержит источник,
точное время с часовым поясом, номер для событий с одинаковым временем,
локальную учётную дату, список команд и ссылки/описание доказательств.
Числа с дробной частью передаются десятичными строками; float во входном
payload отклоняется. Количества проверяются на конечность, неотрицательность
и максимум 18 знаков до вызова существующих функций.

Подключены 12 видов команд: `swap`, `transfer`, `fee`, `create_protocol`,
`top_up_protocol`, `partial_close_protocol`, `close_protocol`, `borrow`,
`repay`, `accrue`, `accrue_interest`, `liquidate`. Финансовые формулы
не скопированы в импортёр: вызываются уже проверенные функции бота.
Команды используют реальные идентификаторы счетов и позиций; созданные
идентификаторы возвращаются в `results` и используются в следующих событиях.
Ссылки на результат предыдущей команды внутри того же пакета пока не поддержаны.

Источник уникален внутри владельца: `(owner_key, source_namespace, source_id)`.
Семейные участники используют один ключ, а не по ключу на каждого участника.
Контур владельца выводится из доступного криптосчёта; идентификатор пользователя
берётся из аутентификации. Перед вызовом проверяются все переданные счета
и позиции. Переводы между разными контурами владельцев в этом журнале пока
не поддерживаются. Обычные собственные счета одного владельца поддержаны.

Точный повтор возвращает сохранённый результат без новых проводок. Это
работает и при одновременных запросах. Изменение исходного события под тем же
ключом отклоняется, включая изменение доказательств. Новый ключ с порядком
раньше либо равным уже проведённому событию отклоняется. Коррекция не может
незаметно встать в конец вместо изменения прошлого.

Порядок — `(occurred_at, order_in_timestamp)` для всего контура владельца;
события разных кошельков предварительно объединяются в один порядок.
Время хранится как timestamptz с микросекундами. Более точные исходные отметки
могут храниться в evidence; порядок задаётся отдельным числом. Учётная дата
может отличаться от UTC-даты максимум на сутки для локального часового пояса.
Она передаётся всем командам; внутренние даты и actor через payload запрещены.

Все новые `operations`, `portfolio_events`, `crypto_liability_events` и
`crypto_protocol_accrual_events` связываются с источником и номером команды
через `crypto_source_event_links`. Связи фиксируются при вставке строк,
поэтому в них не попадают параллельные чужие проводки. Ошибка в любой команде
откатывает журнал, связи и все части события. Контекст источника восстанавливается
перед возвратом: последующие обычные операции не приписываются к импорту.

Создание залога требует реальное списание с исходной позиции. Нельзя выдать
конечное количество или накопленные награды за исходный депозит: прирост
проводится отдельным событием.

`GET /api/v1/crypto/source-events?anchor_account_id=...&limit=50&offset=0`
возвращает журнал доступного владельца в порядке проведения. Пагинация:
1–200 событий. Фильтрация действует по владельцу, не только по одному кошельку.

## Пример контракта (исключительно тестовые идентификаторы и суммы)

```json
{
  "anchor_account_id": 1,
  "source_namespace": "ton-main",
  "source_id": "test-event-001",
  "occurred_at": "2025-01-06T12:00:00.123456+03:00",
  "order_in_timestamp": 0,
  "accounting_date": "2025-01-06",
  "evidence": {"document": "synthetic fixture"},
  "commands": [
    {"kind": "swap", "payload": {
      "position_id": 1, "from_amount": "10", "to_crypto_asset_id": 2,
      "to_amount": "20", "value_in_base": "1500", "valuation_source": "test fill"
    }},
    {"kind": "fee", "payload": {"source_position_id": 1, "quantity": "0.01"}}
  ]
}
```

Воспроизведение повторно должно использовать тот же нормализованный payload:
например, строка `"1"` и число `1` считаются разными входными данными. Результат
содержит `source_event_id`, результаты каждой команды и ссылки на записи.
Это API проведения, а не механизм отправки средств в блокчейн.

## Проверки и воспроизведение

- 132/132 прежних SQL-проверки учёта прошли без изменения их ожиданий.
- 26/26 новых HTTP → storage → SQL проверок: все 12 команд, несколько частей
  одного события, точность, одинаковый момент с разным порядком, повтор,
  конкурентный повтор, изменённые данные/источник, откат второй команды,
  повтор после ошибки, запрет чужого счёта, общий ключ семьи, пагинация,
  запрет переопределения пользователя/даты и импорта конечного состояния.
- Проверены эквивалентные часовые пояса и отсутствие утечки контекста
  источника в обычную операцию через переиспользованное соединение.
- Свежая полная схема + штатный baseline старых миграций; пять общих
  SQL-наборов auth, crypto_assets, fx_lots, money_ledger, scheduled_expenses.
- Обновление схемы коммита `1ddff1f`: миграция 041 реально применена
  (`baseline=false`), повтор запуска успешен. Старые суммы не мигрируются.
- `ruff check backend storage` успешен. Интерфейс в этом проходе не менялся.

Среда — временная PostgreSQL 14; PostgreSQL 17 и полная dev-история остаются
в чеклисте. В HTTP-проверках тестовая личность и упрощённые вспомогательные
таблицы/проверки доступа; это не тест production-аутентификации. Полная схема
проверена отдельно. Производственные данные не менялись.

Воспроизводимый тест: сначала `run_checks.py SOCKET PORT` на пустой временной
базе, затем загрузить `tb/crypto_source_events.sql` и три функции
`capture__crypto_source_event_link`, `put__crypto_source_event`,
`get__crypto_source_events`. Выполнить
`python -m backend.tests.test_crypto_source_events_api SOCKET PORT`.
Машиночитаемый отчёт: `infra/db/Scripts/budgeting/tests/crypto_accounting/source-journal-results.json`.

## Оставшаяся работа без расширения задачи

Общий механизм готов для перечисленных команд, но это ещё не полный импорт:
покупки/продажи за реальные деньги, награды и внешние расходы надо подключить
к нему и проверить. Автоматический пересчёт исправленного прошлого ещё не
реализован: сейчас конфликт безопасно останавливает проведение. Старый
журнал не удаляется и готовые остатки не подставляются.

Порядок и дедупликация гарантированы для вызовов нового журнала. Обычные
старые API пока работают независимо, поэтому dev-прогон должен быть
единственным писателем в выделенные счета. Это не общая блокировка всех
операций пользователя. Режим пересборки должен сохранить это ограничение
или явно контролировать все изменения.

Следующий проход: подключить оставшиеся типы истории и подготовить безопасное
воспроизведение исправленной версии на отдельном dev-контуре. После этого
собирать журнал из прежнего разбора и сверять фактические количества по сотням.
Неизвестные LP-стоимости, общие показатели, Ethereum и итоговый полный прогон
сохраняются в существующих пунктах чеклиста; этот коммит их не закрывает.
