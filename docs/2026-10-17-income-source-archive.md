# Архив источников дохода — 17.10.2026

Уровень **M** + UI/UX-трек. Ветка `claude/income-source-archive`.
Статус: **реализовано, `check.sh` зелёный, ждёт финального ревью и аппрува мержа**.

## Цель

Источник дохода (кнопку-чип в шторке «Пополнить счёт», `IncomeDialog`) можно
убрать в архив. Архивный источник не предлагается при новом доходе. Старые
операции с ним остаются и показываются как раньше («Доход · Зарплата» в
журнале и аналитике).

Не входит в задачу: удаление и переименование источников, архив категорий
расходов (он уже есть, `set__archive_category`).

## Решения владельца (аппрув плана 17.10.2026)

1. Кнопка архива — прямо в шторке «Пополнить счёт».
2. Отдельной кнопки и списка «вернуть из архива» нет. Если нужно вернуть
   источник, его создают заново с тем же именем. Тогда молча оживает
   архивный источник: тот же id, его история и шаблон распределения.

## Что нашли при диагностике

- `income_sources.is_active` в схеме уже был, но выставить `false` было
  нечем: ни функции, ни эндпоинта.
- `put__record_income` уже отклонял неактивный источник («Unknown active
  income source»), и `get__income_source_pattern` тоже требует активный.
  Серверный запрет записывать доход в архивный источник уже был.
- Журнал (`get__operations_history`) и аналитика (`get__operations_analytics*`)
  джойнят `income_sources` без фильтра по `is_active`. Поэтому старые операции
  после архива отображаются без изменений.
- Архив категорий дописывает к имени `[archived N]`. Для источников так нельзя:
  эта приписка попала бы в журнал. Имя остаётся как есть. Конфликт с
  уникальностью `(user_id, name)` при повторном создании решён возвратом
  источника из архива (решение 2).

## Что сделано

1. SQL: новая `func/set__archive_income_source.sql`
   `(_user_id, _income_source_id) → jsonb`. Это `UPDATE ... WHERE user_id = _user_id
   AND is_active`. Чужой или уже архивный источник → исключение.
2. SQL: в `put__create_income_source` добавлено `ON CONFLICT ON CONSTRAINT
   uq_income_sources_user_name DO UPDATE SET is_active = true`. Повтор имени
   возвращает существующий id и оживляет архивный источник. Раньше повтор
   активного имени падал сырой ошибкой, теперь просто выбирается
   существующий источник.
3. API: `POST /api/v1/income-sources/{id}/archive` (как
   `/categories/{id}/archive`), обёртка `Context.set__archive_income_source`.
4. Фронтенд, `IncomeDialog`: справа от «Источник дохода» кнопка
   `dlg-tag-btn` «В архив». Подтверждение — второе нажатие «Точно?», как у
   категорий. После архива выбирается первый оставшийся источник. При
   создании источника, который вернулся из архива, чип не дублируется.
   Новый класс `.fl-row`: строка «подпись + действие». Цвет текста кнопки —
   `var(--text)`, потому что стандартный `--text-2` на `--line` в светлой теме
   даёт 4.4:1 и не проходит axe.
5. Сид `scripts/seed_ui_test.py`: два источника, «Зарплата» и «Фриланс», без
   операций. Существующие снимки «Обзора» не изменились.

## Откат

`git revert` коммитов ветки. Функцию `set__archive_income_source` при этом
нужно удалить миграцией `DROP FUNCTION IF EXISTS
budgeting.set__archive_income_source`: `func/` только пересоздаёт функции из
файлов. Источники, которые успели уйти в архив:
`UPDATE budgeting.income_sources SET is_active = true WHERE ...` (на проде —
только с аппрувом владельца).

## Безопасность

Новое право одно: снять `is_active` у своего источника. Владелец проверяется в
SQL по `user_id` из сессии, а не из тела запроса. Повторное создание
затрагивает только строку с `user_id` вызывающего (уникальный ключ
`(user_id, name)`). Компромиссов нет.

## Открытые вопросы / ограничения

- Список архивных источников нигде не показывается (решение 2). Чтобы вернуть
  источник, нужно помнить его имя.
- Если в архив ушёл последний источник, шторка показывает «Добавьте первый
  источник →», как для нового пользователя.
- axe на всей шторке находит старые нарушения контраста (`--text-3` у `.fl`,
  `.sheet__tag`, `.seg-src__add` и т.д.) и `label` у поля даты. Это тот же
  долг, что в `a11y.spec.ts` `KNOWN`, он относится к задаче design-guide.
  Поэтому новый тест проверяет только новую кнопку.
- Дизайн-ревью отдельной сессией не проводилось: изменение — одна кнопка в
  существующем стиле. Снимки обеих тем просмотрены автором.
