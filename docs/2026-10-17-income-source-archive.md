# Архив источников дохода — 17.10.2026

Уровень **M** + UI/UX-трек. Ветка `claude/income-source-archive`.
Статус: **план, ждёт аппрува владельца**.

## Цель

Источник дохода, или «категорию дохода», то есть кнопку-чип в шторке
«Пополнить счёт» (`IncomeDialog`), можно убрать в архив и вернуть обратно.
Архивный источник не предлагается при новом доходе. Старые операции с ним
остаются и показываются как раньше: «Доход · Зарплата» в журнале и в
аналитике.

Не входит в задачу: удаление источников, переименование, архив категорий
расходов (он уже есть: `set__archive_category`).

## Что уже есть (диагностика)

- `income_sources.is_active` в схеме уже есть (`DATA_MODEL.dbml`), но
  выставить `false` сейчас нельзя: ни функции, ни эндпоинта нет.
- `put__record_income` уже отклоняет неактивный источник («Unknown active
  income source»). Запрет «нельзя записать доход в архивный источник» уже
  работает на сервере, его достаточно покрыть тестом.
- `GET /api/v1/income-sources?is_active=true|false` уже фильтрует.
- Журнал (`get__operations_history`) и аналитика (`get__operations_analytics*`)
  джойнят `income_sources` без фильтра по `is_active`. Значит, старые операции
  после архива отображаются без изменений.
- Архив категорий расходов (`set__archive_category`) дописывает к имени
  `[archived N]`. Для источников так делать **нельзя**: журнал показывал бы
  «Доход · Зарплата [archived 5]». Имя остаётся как есть.
- UI-паттерн архива уже есть в `Settings.tsx` у инвестиционных счетов:
  переключатель «Архив · N» / «Активные счета» под списком и кнопка
  «В архив» / «Восстановить». Его и переиспользуем.

## Решение

**БД.** Схема не меняется, миграции нет. Новая функция
`func/set__income_source_active.sql`:
`set__income_source_active(_user_id, _income_source_id, _is_active) → jsonb`.
Она проверяет, что источник принадлежит `_user_id` (иначе исключение),
выставляет `is_active` и возвращает `{id, name, is_active, created_at}`.
Шаблон распределения (`income_source_patterns`) не трогается и возвращается
вместе с источником.

**API.** `PUT /api/v1/income-sources/{id}/active` с телом `{is_active: bool}`.
Это та же форма, что у `PUT .../crypto-assets/{id}/hidden`.

**Фронтенд, `IncomeDialog`:**
- Чипы показывают только активные источники, как сейчас.
- У выбранного чипа в области распределения появляется маленькая кнопка
  «В архив». Подтверждение — тем же двойным нажатием «В архив» → «Точно?»,
  что у категорий (`CategoryDialog`). После архива выбор переходит на первый
  активный источник.
- Под чипами, если в архиве что-то есть, показывается ссылка-переключатель
  «Архив · N» (как `invest-archive-toggle`). Она раскрывает список архивных
  источников. У каждого — кнопка «Вернуть». После возврата источник снова
  становится чипом и выбирается.
- Архивные источники загружаются вторым запросом `?is_active=false` вместе с
  активными при открытии шторки.

**Новый источник с именем архивного.** Уникальность `(user_id, name)`
остаётся, и сейчас такое создание падает сырой ошибкой. См. вопрос 2.

## Критерии приёмки

1. Владелец источника может перевести его в архив и вернуть (`is_active`
   меняется в БД).
2. Чужой источник ни архивировать, ни вернуть нельзя: исключение / 4xx.
3. Доход в архивный источник не записывается (`put__record_income` падает).
   После возврата — записывается.
4. Операции с архивным источником остаются в журнале с прежним именем
   источника (`income_source_name` не меняется).
5. `GET /income-sources` (по умолчанию активные) не возвращает архивный
   источник, а `?is_active=false` возвращает.
6. В шторке «Пополнить счёт» архивного чипа нет. «Архив · N» показывает его,
   «Вернуть» возвращает его в чипы.
7. Шаблон распределения у источника сохраняется после архива и возврата.

## Откат

`git revert` коммитов ветки и миграция
`DROP FUNCTION IF EXISTS budgeting.set__income_source_active`: `func/`
только пересоздаёт функции из файлов, а лишние сам не удаляет. Данные: источники, которые успели уйти в архив, вернуть
`UPDATE budgeting.income_sources SET is_active = true WHERE ...` (на проде —
только с аппрувом).

## Безопасность

Единственное новое право — менять `is_active` своего источника. Проверка
владельца в SQL-функции по `user_id` из сессии, а не из тела запроса.
Компромиссов нет.

   дохода» в «Настройках» со списком и архивом, как у инвестсчетов. Шторка —
   ок?

   вернуть архивный источник из архива и выбрать его: история и шаблон
   распределения продолжаются. Альтернатива — показать ошибку «Такой источник
   есть в архиве — верните его». Какой вариант?
