# Отмена операций «как в банке» — 17.10.2026

Уровень **L** + UI/UX-трек: деньги, схема БД (новая таблица), SQL-функции
реверса и истории, экраны списка операций. Ветка `claude/cancel-operations`.

## Цель

Сейчас операцию отменяют двумя разными путями:

- **Банковские операции** (доходы, расходы, переводы, распределения, обмен) —
  в общем списке операций (`Operations.tsx`): строка раскрывается, кнопка
  «Отменить» сразу, без подтверждения, делает сторно
  (`put__reverse_operation`). Отменённая строка остаётся в списке с меткой
  «Отменена».
- **Ручные операции крипты и коллекций** (`manual-portfolio-v1`,
  `manual-collection-v1`) — только через отдельную шторку «История операций»
  (`CryptoCorrectionSheet`, кнопка над списком во вкладке «Портфель →
  Операции»). Она дублирует тот же список. Удаление откатывает строки учёта
  (`put__delete_crypto_source`), и операция **исчезает** из списка.

Нужно сделать один путь, как в банковском приложении:

1. Убрать «Историю операций» и всё, что нужно только ей.
2. Нажатие на операцию в обычном списке открывает её детали с кнопкой
   «Отменить».
3. Отменённая операция не исчезает: остаётся в списке и выглядит отменённой.
   Влияние на балансы откатывает существующая логика (сторно для банковских,
   откат журнала для крипты и коллекций).
4. Повторно отменить нельзя. Если отменить нельзя, причина видна в деталях
   понятным текстом по-русски, до нажатия.

## Не входит

- Изменение самой логики отката: правила зависимостей
  `put__delete_crypto_source` и проверки баланса сторно остаются как есть.
  Меняются только тексты ошибок (по-русски) и то, что остаётся видно в списке.
- Отмена импортированных операций (`first-hundred-dev-v1`,
  `history-update-2026-09-28`) инвестиционных типов — по-прежнему нельзя,
  теперь с понятной причиной.
- Отмена событий журнала, у которых нет строки в `operations` и которых поэтому
  нет в списке (см. вопрос владельцу 2).
- Две операции, удалённые 16.10 через «Историю операций»
  (`crypto_source_deletions`, 2 строки на проде), в списке не появятся: снимка
  для них нет. Они остаются в аудите.
- Показ строк-сторно («Отмена операции #N») — уже скрыт во встроенном списке и
  фильтром банковского списка, не меняется.

## Как устроено сейчас (диагностика)

- `put__reverse_operation(_user_id, _operation_id)`:
  - если операция связана (`crypto_source_event_links`) с событием
    `manual-portfolio-v1` / `manual-collection-v1` — вызывает
    `put__delete_crypto_source`. Строки события, включая саму строку
    `operations`, удаляются, конверт и мутации уходят в
    `crypto_source_deletions`;
  - иначе — сторно: новая операция `reversal`, противоположные проводки.
    Проверки баланса на уменьшаемой стороне (`DEVELOPMENT_GUIDELINES.md` §3),
    лотов, кредитного лимита, свободного бюджета, порядка платежей по кредиту.
    Тексты ошибок английские («Cannot reverse operation 5, insufficient bank
    balance in currency RUB»), API отдаёт их как есть (`main.py`, `RaiseError` →
    400), интерфейс показывает сырой текст;
  - инвестиционные типы вне ручного журнала — «Investment operations reversal is
    not supported yet».
- Список `get__operations_history` строит строки из `operations` +
  `bank_entries` / `crypto_bank_entries` / `budget_entries` / `portfolio_events`.
  Флаг `has_reversal` → метка «Отменена» и стиль `op-row--cancelled`. Для
  инвестиционных типов `isCancellable` в `Operations.tsx` кнопку не показывает.
- Прод (readonly, 17.10): ручных событий 756 коллекций и 44 крипты. Без строки
  `operations` — 260 `collectible_details` (правка параметров предмета) и 14
  событий крипты (`repay`, `close_protocol`, `protocol_yield`, `observation`,
  `fee`, `receive_unknown` и др.). У каждого ручного события не больше одной
  строки `operations`.
- Только «Историей операций» используются:
  - фронтенд: `CryptoCorrectionSheet.tsx`, кнопка и состояние
    `correctionsOpen` в `Portfolio.tsx`, `.pf-ops-tools` и `cx-*` в
    `styles.css`, `fetchCryptoCorrectionHistory`, `deleteCryptoSource`,
    `CryptoEditableSource` в `api.ts`, `browser-tests/undo.spec.ts`;
  - API: `GET /crypto/correction-history`, `DELETE /crypto/source-events/{id}`
    и их обёртки в `storage/ledger.py`;
  - SQL: `get__crypto_correction_history` (и её вызов в
    `tests/collectible_journal.sql`).
  - `put__delete_crypto_source` остаётся: её вызывает `put__reverse_operation`.

## Решение

### 1. Снимок отменённой операции журнала — таблица `cancelled_operations`

Откат журнала физически удаляет строку `operations` и её проводки — так
балансы гарантированно возвращаются к прежним (проверенный механизм). Чтобы
операция осталась в списке, перед откатом сохраняется её снимок — ровно та
строка истории, которую видел пользователь:

```
cancelled_operations
  operation_id      bigint PK       -- id удалённой строки operations
  deletion_id       bigint FK → crypto_source_deletions(id) ON DELETE CASCADE
  owner_type, owner_user_id, owner_family_id   -- как в operations
  operated_on       date
  created_at        timestamptz     -- исходные, для сортировки в списке
  item              jsonb           -- строка get__operations_history на момент отмены
  cancelled_by_user_id bigint FK users ON DELETE SET NULL
  cancelled_at      timestamptz default now()
```

Миграция `056_cancelled_operations.sql` + `tb/`. Данные не трогаются.

- `get__operations_history` получает необязательный параметр
  `_operation_ids bigint[]`: ограничивает выборку этими id. Им пользуется
  `put__delete_crypto_source`: до отката снимает строки истории для операций
  события и после записи в `crypto_source_deletions` кладёт их в
  `cancelled_operations`. Отдельного «рендера» строки не появляется.
- `get__operations_history` объединяет живые операции и снимки (до
  сортировки и пагинации). Для снимка `has_reversal = true`, добавляется
  `is_cancelled_snapshot = true`. Фильтры (`investment`, `banking`,
  `cancelled`, тип, вид актива) для снимков считаются по полям `item`
  (`type`, `bank_entries[].bank_account_kind`, `investment_asset_type`
  счёта, `portfolio_events[].position_asset_type_code`). Для этого в снимок
  проводок добавляется `investment_asset_type` счёта.

Банковские операции уже остаются в списке за счёт сторно и `has_reversal` —
для них ничего не меняется.

### 2. Повторная отмена и понятные причины

- `put__reverse_operation`: если `_operation_id` есть в `cancelled_operations`
  → «Операция уже отменена». Сторно уже отменённой — тот же текст вместо
  «Operation % has already been reversed».
- Все `RAISE` в `put__reverse_operation` и пользовательские тексты
  `put__delete_crypto_source` переводятся на русский и говорят «отмените»,
  а не «удалите»:
  - не хватает денег на счёте: «Не отменить: на счёте «<имя>» не хватает
    <сумма> <валюта> — деньги уже потрачены»;
  - кредитный лимит: «Не отменить: на кредитной карте «<имя>» будет превышен
    лимит»;
  - монеты / лоты: «Не отменить: полученные монеты (валюта) уже потрачены»;
  - свободный бюджет: «Не отменить: в свободном остатке не хватает <сумма>»;
  - платёж по кредиту: «Сначала отмените более поздние платежи по этому кредиту»;
  - импорт инвестиций: «Эту операцию нельзя отменить: она загружена из истории
    портфеля»;
  - журнал: «Сначала отмените более поздние операции, которые её затрагивают:
    <дата, вид>». Виды команд переводятся на русский на фронтенде (словарь
    `kinds` из `CryptoCorrectionSheet` переносится в `utils/`).
- Проверка до нажатия — `get__operation_cancel_check(_user_id,
  _operation_id) → {can_cancel, reason}`: вызывает `put__reverse_operation`
  внутри блока `BEGIN … EXCEPTION`, в конце поднимает служебную ошибку, и
  подтранзакция откатывается. Так причина всегда совпадает с настоящей
  отменой — вторую копию правил писать не нужно. Ошибка доступа не
  маскируется в `reason`, а пробрасывается.
- API: `GET /operations/{id}/cancel-check` → `{can_cancel: bool, reason:
  str | null}`. Отмена — прежний `POST /operations/reverse`.

### 3. Интерфейс

- `Operations.tsx` (общий и встроенный в «Портфель → Операции» список): строка
  по нажатию открывает шторку деталей `OperationDetailSheet` (`BottomSheet`)
  вместо раскрытия на месте. В шторке — то, что сейчас в раскрытой строке
  (сумма, дата, счёт, комментарий, проводки, события портфеля), плюс:
  - отменённая: метка «Отменена», кнопки нет;
  - можно отменить: «Отменить операцию» → подтверждение в шторке «Отменить
    операцию? Балансы вернутся к состоянию до неё» → «Отменить» / «Назад»;
  - нельзя: кнопки нет, вместо неё причина из `cancel-check`;
  - проверка грузится: кнопка неактивна, «Проверяем…»;
  - ошибка при отмене: текст в шторке (`tk-error`), шторка открыта.
  После отмены список перезагружается, строка остаётся с меткой «Отменена».
- Убираются: `CryptoCorrectionSheet.tsx`, кнопка «История операций»,
  `correctionsOpen`, `HistoryIcon` (если больше не нужен), стили
  `.pf-ops-tools`, `.cx-*` (если не используются в другом месте),
  `fetchCryptoCorrectionHistory`, `deleteCryptoSource`, `CryptoEditableSource`.
  В `Portfolio.tsx` встроенному списку после отмены нужно обновить портфель:
  добавляется `onChanged` → `loadPortfolio()`.
- `isCancellable` на фронтенде больше не решает за сервер: для неотменённых
  операций кнопку/причину определяет `cancel-check`.

### 4. Удаление дублирующего API и SQL

- `GET /crypto/correction-history`, `DELETE /crypto/source-events/{id}`,
  `ledger.get__crypto_correction_history`, `ledger.put__delete_crypto_source`.
- `get__crypto_correction_history`: `DROP FUNCTION` в миграции 056, файл
  удаляется; блок в `tests/collectible_journal.sql` переписывается на
  `get__operations_history`.

## Критерии приёмки

1. В интерфейсе нет «Истории операций»; `GET /crypto/correction-history` и
   `DELETE /crypto/source-events/{id}` отвечают 404/405;
   `get__crypto_correction_history` в схеме нет.
2. Продажа предмета (`manual-collection-v1`) отменяется через
   `put__reverse_operation`: позиция снова открыта, проводки и остатки как до
   продажи (как в тестах удаления), а в `get__operations_history` строка с тем
   же `operation_id`, суммой и датой осталась, `has_reversal = true`.
3. Снимок попадает в фильтры: `investment` + вид актива `collectible`,
   `cancelled`; не попадает в `banking`, если в нём нет неинвестиционных
   счетов; не виден чужому пользователю; виден члену семьи для семейной
   операции. Пагинация и `total_count` учитывают снимки.
4. Повторная отмена отменённой — «Операция уже отменена»: и для снимка
   журнала, и для банковской операции со сторно. Данные не меняются.
5. `cancel-check`:
   - отменяемая операция → `can_cancel = true`, после вызова данные не
     изменились (ни сторно, ни удаления, ни строк в `crypto_source_deletions`);
   - доход, деньги которого потрачены → `false` и русская причина про
     нехватку денег на счёте;
   - журнальная операция с более поздней зависимой → `false`, причина
     называет более позднюю операцию;
   - уже отменённая → `false`, «Операция уже отменена»;
   - чужая операция → ошибка доступа, не `reason`.
6. Все тексты ошибок `put__reverse_operation`, видимые пользователю, — по-русски.
7. В интерфейсе: нажатие на операцию открывает шторку деталей; «Отменить
   операцию» → подтверждение → строка в списке с меткой «Отменена», баланс
   обновился. Для неотменяемой операции в шторке причина и нет кнопки. Для
   отменённой — метка и нет кнопки.
8. Банковская отмена работает как раньше (сторно), только через шторку и с
   подтверждением.

## Известные уязвимости / осознанные риски

- Проверка `cancel-check` — это настоящая отмена, откатываемая в
  подтранзакции. На время вызова (миллисекунды) она берёт те же блокировки,
  что и отмена журнала (`LOCK … SHARE ROW EXCLUSIVE` на таблицах учёта), и
  ненадолго задерживает параллельные записи. Это GET с побочным эффектом
  блокировок, но без изменений данных (критерий 5 проверяет это тестом).
  Альтернатива — дублировать правила проверки в отдельной функции — хуже:
  причины разойдутся с реальной отменой.
- Снимок — копия строки истории на момент отмены. Если позже переименуют счёт
  или предмет, в отменённой строке останется старое имя. Для банковских
  выписок это нормально.

## Ревью плана

Свежая сессия без контекста чата, 17.10.2026, ветка `claude/cancel-operations`
на коммите `d517900`. Поведение подтранзакции проверено на одноразовой
транзакции в локальном `postgres:17`: после перехвата служебной ошибки
`pg_advisory_xact_lock`, `LOCK TABLE … SHARE ROW EXCLUSIVE`,
`set_config(…, true)` и `CREATE TEMP TABLE … ON COMMIT DROP` откатываются.
Сама идея dry-run работоспособна. Ниже — что нужно уточнить.

1. **Исправить: по умолчанию отменённые операции в общем списке скрыты.**
   `bankingTypeFilter` и `historyTypeFilter` стартуют с
   `income, expense, exchange` без `cancelled` (`frontend/src/pages/Operations.tsx:848-854`),
   а клиентский фильтр выбрасывает строки с `has_reversal`
   (`Operations.tsx:1083-1100`). «Операции» на главной — это

2. **Исправить: как отличить ошибку доступа в `cancel-check`.** Сейчас доступ
   и «не найдено» — обычный `RAISE` (P0001) с текстом

   `get__operation_cancel_check` **сама** проверяет доступ до dry-run через

   `cancelled_operations`. Нет ни там, ни там — та же ошибка доступа. Внутри
   dry-run ловить только `WHEN raise_exception` (P0001) и служебный SQLSTATE.
   `WHEN OTHERS` не использовать: иначе deadlock,
   `serialization_failure` или нарушение ограничения превратятся в «причину».

3. **Исправить: порядок проверок «уже отменена» в `put__reverse_operation`.**
   Строки `operations` у снимка уже нет, поэтому сначала сработает
   `Unknown operation` (`put__reverse_operation.sql:41-43`). Проверку
   `cancelled_operations` надо поставить до неё, а доступ брать из owner-полей

   «already reversed» (`put__reverse_operation.sql:78-84`) читает без
   блокировки исходной строки. Уникального индекса на
   `operations.reversal_of_operation_id` нет (`tb/operations.sql:11,49-50`

## Решения по ревью плана (автор)

Все пункты «исправить» принимаются. Изменения плана:

- **Видимость в банковском списке (п. 1, 9).** Отменённые показываются в
  банковском списке по умолчанию: `cancelled` входит в начальный набор
  фильтров. Фильтр «Отменённые» остаётся, им их можно скрыть.
- **Доступ в `cancel-check` (п. 2).** `get__operation_cancel_check` сама
  проверяет доступ (`has__owner_access`) по `operations`, а если строки нет —
  по `cancelled_operations`; нет ни там ни там → «Операция не найдена». Внутри
  dry-run ловятся только `raise_exception` (P0001) и служебный SQLSTATE, без
  `WHEN OTHERS`.
- **«Уже отменена» (п. 3, 4).** В `put__reverse_operation` первым шагом:
  есть снимок → проверка доступа по его owner-полям → «Операция уже
  отменена». Строка `operations` берётся `FOR UPDATE`, поэтому двойное сторно
  при гонке невозможно. В `put__delete_crypto_source` «Операция не найдена»
  при наличии снимка заменяется на «Операция уже отменена».
- **Снимок всегда (п. 5).** Строка `cancelled_operations` пишется для каждой
  операции события; `item` может быть NULL (операция была скрыта на архивных
  счетах — в списке её нет и после отмены).
- **Фильтры колонками (п. 6).** При снимке пишутся готовые колонки
  `is_investment`, `is_banking`, `asset_types text[]`, вычисленные теми же
  выражениями, что живые фильтры (общая SQL-функция-предикат по
  `operation_id`, вызывается до отката). Тест: операция видна в каждом фильтре
  до отмены ⇔ видна после.
- **Устойчивость к старым снимкам (п. 7).** `has_reversal` и
  `is_cancelled_snapshot` подставляются при чтении, а не хранятся в `item`.
  Новые поля модели ответа — необязательные с умолчанием. Правило «снимок
  JSON читается старым и новым кодом: новые поля только необязательные»
  дописывается в `DEVELOPMENT_GUIDELINES.md` §9.
- **Сигнатура (п. 8).** `DROP FUNCTION IF EXISTS` для новой 6-аргументной
  сигнатуры; `_operation_ids` в API не выставляется.
- **Тексты (п. 10).** Отказ по инвестиционным типам: «Эту операцию нельзя
  отменить: для неё отмена пока не поддерживается». Переводятся все `RAISE`
  `put__reverse_operation`, включая привязку к карточной оплате.
- **Список удаляемого (п. 11)** дополнен: перевод в `api.ts`, `opsVersion`/`key`
  (вместо перемонтирования — `onChanged`), `location …/correct` в
  `infra/nginx.conf`, старые тексты в SQL-тестах.
- **Риски (п. 12, 13)** дописываются в «осознанные риски»: dry-run тратит
  значения последовательностей и на миллисекунды берёт блокировки 18 таблиц;
  повтор `POST /reverse` после сетевой ошибки получает «уже отменена», фронтенд
  тогда просто перезагружает список.

На проде таких ручных событий крипты 14 (`repay`, `close_protocol`,

- `get__cancel_snapshot` написана на PL/pgSQL, а не на SQL: тело SQL-функции
  проверяется при создании, а `get__operations_history` при сборке схемы идёт
  по алфавиту позже.
- В PL/pgSQL одна запись (`record`) для `SELECT … INTO` из таблиц с разными
  типами колонки (`varchar` в `operations`, `text` в снимке) падает «type of
  parameter does not match». Используются отдельные переменные.
- axe в шторке: `.sheet__tag` (тег всех шторок, токен `--text-3`) — известная
  проблема из `a11y.spec.ts`, пропущена в тесте с комментарием. Подзаголовок
  шторки переведён на `--text-2`, чтобы не добавлять новое нарушение.

### Отклонения от плана

- Шторка — локальный компонент в `Operations.tsx`, не отдельный файл (см. выше).
- Банковские операции отменяются через тот же `put__cancel_operation`; для
  них поведение прежнее (сторно).

## Известные уязвимости / осознанные риски (итог)

- `cancel-check` — настоящая отмена в откатываемой подтранзакции. На время
  вызова (миллисекунды) она берёт те же блокировки, что и отмена журнала
  (`LOCK … SHARE ROW EXCLUSIVE` на 18 таблицах), и ненадолго задерживает
  параллельные записи. Тратит значения последовательностей (`nextval` не
  откатывается). Данные не меняются — проверено тестом.
- Снимок отмены вызывает историю 21 раз (фильтры). На объёмах личного учёта
  это миллисекунды; помечено `ponytail:` в `get__cancel_snapshot.sql`.
- Снимок — копия строки на момент отмены: переименование счёта или предмета
  позже в отменённой строке не отразится.
- Повтор `POST /reverse` после потерянного ответа получает «Операция уже
  отменена»; фронтенд в этом случае считает отмену выполненной и
  перезагружает список.
