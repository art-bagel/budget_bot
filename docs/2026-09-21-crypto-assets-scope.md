# Общий справочник крипто-активов: закрыть переписывание чужих записей

Дата: 2026-09-21

## Цель

`ISSUES` п.5 — последний из критических. `crypto_assets` общая на всех
пользователей, а публичный `POST /api/v1/crypto/assets` стоял на `upsert` с
`DO UPDATE`.

## В чём была проблема

Функция `put__upsert_crypto_asset` при конфликте переписывала `name`,
`decimals` и мержила `metadata`. В `metadata` лежит `coingecko_id` — и он в
приоритете над захардкоженным маппингом:

```python
def _coingecko_id_for_asset(asset):
    explicit_id = metadata.get('coingecko_id') or metadata.get('coin_gecko_id')
    if isinstance(explicit_id, str) and explicit_id.strip():
        return explicit_id.strip().lower()
    return COINGECKO_IDS_BY_SYMBOL.get(...)   # безопасный запасной вариант
```

То есть любому аутентифицированному пользователю достаточно было одного
запроса `symbol=BTC, metadata={"coingecko_id": "<что угодно>"}`, чтобы у
**всех** пользователей оценка биткоина поехала на цену произвольной монеты.
Ни исключения, ни следа в логах: просто у всех портфелей меняются цифры.

Дополнительно переписываемые `decimals` искажают отображение количеств.

## Что решило задачу

Ключевое наблюдение: **фронт этот эндпоинт не вызывает**. `upsertCryptoAsset`
был экспортирован в `frontend/src/api.ts`, но не импортировался ниоткуда —
UI везде только выбирает из готового списка (`cryptoAssets.find`,
`[...cryptoAssets].sort`). То есть у запрета на переписывание нулевая цена
по функциональности.

Разделены два пути:

| путь | функция | семантика |
|---|---|---|
| публичный (HTTP) | `put__ensure_crypto_asset` | `DO NOTHING` — заводит новое, существующее возвращает как есть |
| привилегированный (прямой SQL) | `put__upsert_crypto_asset` | `DO UPDATE` — для скриптов `budgeting/manual/` |

Обёртка на `put__upsert_crypto_asset` в `storage/ledger.py` убрана, поэтому
из API привилегированный путь теперь физически недостижим — не флагом,
который можно случайно передать, а отсутствием кода.

На самой `put__upsert_crypto_asset` оставлено предупреждение в шапке: она
остаётся нужной скриптам импорта и выглядит безобидно, если не знать истории.

## Состояние прода

Проверено чтением: 4 засеянных актива (TON, USDT, BTC, ETH), у всех
`metadata = {}`, все созданы в день сида. Эндпоинтом никто ни разу не
пользовался, чистить нечего. Цены сейчас берутся из захардкоженного
`COINGECKO_IDS_BY_SYMBOL`.

## Что проверено

- `tests/crypto_assets.sql`: публичный путь не меняет ни имя, ни `decimals`,
  ни `coingecko_id`; дубликат не создаётся; новый актив по-прежнему
  заводится; повторный вызов не переписывает только что созданное;
  валидация тикера и `decimals` на месте; привилегированный путь всё ещё
  умеет править справочник.
- Мутация `DO NOTHING` → `DO UPDATE` (возврат к уязвимому поведению)
  ловится тестом.
- Схема с нуля: 134 функции, все пять SQL-тестов и API-тест проходят.
- Фронт: `tsc -b` чисто, лишних предупреждений не добавилось.

## Известные уязвимости / осознанные риски

Компромиссов не вносилось — это чистое ужесточение.

Один побочный эффект, который стоит знать: **исправить уже заведённый актив
через API теперь нельзя**. Если кто-то заведёт новый актив с опечаткой в
`coingecko_id`, поправить его сможет только владелец через прямой SQL. Для
общей на всех таблицы это правильная сторона размена, но это именно размен,
а не бесплатный выигрыш.

## Открытые вопросы

- Новые активы по-прежнему может завести любой пользователь. Поток «завести
  тысячу мусорных тикеров» ничем не ограничен — rate limiting в проекте
  отсутствует целиком (`ISSUES` п.14). Отравить существующий актив больше
  нельзя, засорить справочник — можно.
- `metadata` при создании принимается как есть, без схемы. Сейчас оттуда
  читается только `coingecko_id`, но проверки, что там лежит, нет.
- Маппинг `MATIC → matic-network` не проверен после миграции токена в POL
  (`ISSUES` п.10).
