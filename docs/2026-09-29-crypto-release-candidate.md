## Как собран кандидат

1. Сняты дампы review, dev и прежней репетиции с SHA256, зафиксированы образы и
   git SHA. Существующие доказательства не менялись.
2. Дамп production снят потоком: `ssh … 'sudo docker exec budget_bot_db pg_dump
   -U budget -d budget -Fc --no-owner --no-privileges' > …` — ничего не пишется
   на хост. SHA256 `dc8b211a…720a4`, PostgreSQL 17.11.
3. Восстановлен в две локальные базы: эталон `crypto_prod_20260928_211943`
   (не меняется) и рабочую `crypto_release_20260929`.
4. Миграции 036–049 и функции применены штатным `run_migrations.sh` из ветки,
   как это сделает деплой; они записаны в `schema_migrations`, поэтому деплой
   не выполнит их повторно. Проверено: миграции не изменили ни одного значения
   (различия только в масштабе numeric).
5. `rehearse_release.py`: прежняя подготовка (архив заменяемого криптографа,
   отмена 19911 без дохода, остаток 5 318 633,57 RUB, освобождено
   2 247 804,43 RUB — совпадает с исходным состоянием); серверная покупка 21225
   сохраняет ID; идентичности вставок берутся из review, занятые новыми
   строками production перенумерованы (+2 000 000: 2 операции, 1 банковская
   и 3 бюджетные проводки, ссылок на них в метаданных нет).
6. Воспроизведение 2033 источников по порядку журнала. Источники, записанные до
   исправления 304bed1, воспроизводятся той версией `put__settle_crypto_fiat_sale`,
   которая их создала; затем 2289 выполняется текущей, как в review. Иначе
   защита идентичностей отвергает изменение структуры проводок; её не
   ослабляли. После replay проверяется, что в базе ровно функции ветки.
7. Проверки в той же транзакции, до фиксации: все 13 840 строк вне
   заменяемого набора неизменны (разрешены только настройки криптосчетов
   владельца, алиас USDT и остатки USD-лотов банка); каждая операция
   production ровно один раз; новых доходов нет; кошельки, DeFi, лоты,
   события портфеля и банковская крипта совпадают с review; стоимость каждого
   USD-расхода совпадает с review; банк и бюджет = review − исключённое +
   только-production; связанные платежи используют свой лот; нет
   отрицательных лотов; FX-лоты = остаткам; все последовательности впереди
   таблиц; повтор всех 2033 запросов и обычного вызова расчёта подарка ничего
   не меняет.
8. Кандидат выгружен (`candidate.dump`, SHA256 `6aa5870d…8922d`), восстановлен в
   `crypto_release_20260929_restore_check`: 42 таблицы, функции, триггеры и
   последовательности совпали по дайджесту содержимого.

Воспроизводимость: `prepare_release_candidate.sh <дамп> <метка>` выполняет
шаги 3–8 одной командой (~3 мин). Проверен на имитации финального снимка с
двумя новыми обычными операциями: найдены и перенесены автоматически, банк
и свободный остаток изменились ровно на их суммы, дайджест восстановления
совпал.

## Найдено по ходу

- **Отставшая последовательность.** В первой сборке `bank_accounts_id_seq`
  осталась на 94 при счетах до 129: первое создание счёта в production упало бы.
  Прежний скрипт это делал, адаптация потеряла; исправлено, добавлена общая
  проверка всех последовательностей. Правило внесено в DEVELOPMENT_GUIDELINES.
- **CI остановил бы деплой.** `tests/crypto_account_settings.sql` требовал
  пользователя dev-базы и падал на пустой схеме CI с `ON_ERROR_STOP`. Тест
  сделан самодостаточным. Локальный эквивалент CI (сборка frontend, lint,
  ruff, py_compile, синтаксис shell, схема с нуля + все SQL-тесты, API-тест
  авторизации, `docker compose config`) проходит; бэкенд компилируется в
  образе на Python 3.10.
- **Права.** В production есть роль `agent_readonly` (через `pg_read_all_data`
  и явный CONNECT на базу; подключается MCP с этого Mac). Дамп без привилегий
  этого не переносит — при переключении нужен явный `GRANT CONNECT`.
- **Названия счетов.** Кандидат, как и прежняя репетиция, берёт настройки
  криптосчетов из review: 87 «Tangem  Wallet» → «Холодный кошелёк», 92
  «Main TON» → «Основной TON-кошелёк». Нужно подтверждение владельца.

## План переключения (после разрешения)

Ожидаемая недоступность — **20–30 минут**, в основном сборка кандидата и CI.
Время: не на :15 (почасовой бэкап держит соединение с базой).

1. Подготовка без простоя: на хосте `docker tag infra-api:latest
   infra-api:pre-crypto-20260929` и то же для `infra-web`; копия `infra/.env`
   с правами 600. Текущий код production — `ae29940`.
2. Остановить запись: `docker compose -f infra/docker-compose.yml --env-file
   infra/.env stop api web`. Планировщик живёт в API, запланированных расходов
   нет. Убедиться, что в `pg_stat_activity` нет соединений API, а максимум
   `operations.id` не растёт.
3. Финальный дамп потоком на Mac, SHA256, `pg_restore -l`.
4. Локально: `scripts/crypto/prepare_release_candidate.sh <дамп> <метка>`.
   Он сам находит новые операции production и повторяет все проверки. Если
   упал — вернуть `docker compose start api web`, production не изменён.
5. Загрузить кандидат в новую базу на том же сервере: `createdb -U budget
   budget_crypto_<метка>`, `pg_restore --no-owner --no-privileges` из потока
   по SSH, `GRANT CONNECT ON DATABASE … TO agent_readonly`.
6. `release_digest.sql` на новой базе production должен совпасть с локальным
   `digest.txt` построчно.
7. Переключение, подключившись к `postgres`: `ALTER DATABASE budget WITH
   ALLOW_CONNECTIONS false`; завершить оставшиеся соединения к `budget`;
   `ALTER DATABASE budget RENAME TO budget_pre_crypto_<метка>`;
   `ALTER DATABASE budget_crypto_<метка> RENAME TO budget`. Имя в env и секретах
   CI не меняется; старая база остаётся рядом, закрытой для подключений.
8. Код: слить ветку в `main` (конфликтов нет, проверено `merge-tree`) и
   `git push origin main`. CI: проверка, дамп перед миграциями, `run_migrations`
   (миграций нет, функции те же), сборка и запуск API/web. Push только после
   шага 7: иначе CI накатит миграции на старую базу.
9. Сразу после деплоя: `/health`; API подключён к `budget`; дайджест совпадает
   с кандидатом (кроме сессий, если уже был вход); контрольные суммы таблицы
   «Итог». Затем владелец открывает бот; проверяем банк, USDT, подарок,
   распределение, криптосчета, DeFi, историю и бэкап в :15.
10. Отчёт о выпуске, R6 закрыт.

Запись открывается запуском API в конце CI. Если нужно исключить
действия других членов семьи до проверки, их надо предупредить заранее.

## Откат

- **До шага 7** production не изменён: `docker compose start api web`.
- **После 7, до открытия записи**: остановить api/web; переименовать `budget`
  в `budget_crypto_<метка>_failed`, `budget_pre_crypto_<метка>` обратно в
  `budget` и разрешить подключения; `docker tag infra-*:pre-crypto-20260929
  infra-*:latest`, `docker compose up -d --no-build api web`. Если `main`
  уже запушен — сделать revert слияния до любого следующего push, иначе CI
  снова выкатит новый код на старую базу. Последовательность переименований
  вперёд и назад, с закрытием активного соединения, отрепетирована локально
  на временных базах; старая база при переключении не изменяется.
- **После открытия записи**: сначала остановить запись и снять дамп новой базы.
  Старую базу не возвращать вслепую — либо исправление вперёд, либо
  восстановление с явным переносом новых операций.

## Известные уязвимости / осознанные риски

- Запись открывается вместе со стартом API в CI; проверки после деплоя
  идут уже при открытом доступе. Вся финансовая приёмка выполняется раньше,
  на базе до запуска API (дайджест = проверенный кандидат).
- Старая база хранится на том же сервере Postgres. Независимые копии:
  финальный дамп на Mac и почасовой бэкап в MinIO.
- Кандидат собирается на локальном PostgreSQL 17.10 и восстанавливается в
  17.11 (один мажор, формат дампа совместим).
- Для проверки интерфейса локально поднимался стенд без токена бота (принимает
  dev-заголовок пользователя), только на 127.0.0.1 и на одноразовой копии.
  Остановлен; тестовая сессия и токен удалены.
- Во время replay внутри транзакции временно загружается прежняя версия
  функции расчёта; фиксация возможна только если в конце функции совпадают
  с веткой.
