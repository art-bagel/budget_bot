# Мгновенный старт: без принудительного сплэша, обзор из кэша

Ветка `claude/instant-start` (от `origin/main` 3364fe5). Уровень **L**:
интерфейс и деньги на экране не меняются, но в хранилище устройства
появляются финансовые данные (безопасность), поэтому план проходит ревью.

## Разбор P6 (05.11.2026)

Что нашлось в коде:

- Страницы уже грузятся лениво (`React.lazy` в `App.tsx`), ремаунта страниц
  по ключу больше нет: `refreshKeys` стал токеном обновления. Остался один
  `key={familyRefreshKey}` в `Settings.tsx`. Часть пунктов
  `docs/IMPROVEMENTS.md` про фронтенд устарела.
- Данные грузятся сырым `fetch` в `useEffect` каждой страницы. Каждый переход
  на вкладку перезапрашивает её целиком, но показывает прежние данные с
  `RefreshBar`. Кэша между запусками нет.
- `useAuth` держит сплэш минимум 2 с (`MIN_SPLASH_MS = 2000`), даже если
  контекст пришёл за 200 мс. Потом `Dashboard` показывает свой сплэш, пока
  грузит обзор: 6 запросов плюс снимок по каждому инвестиционному и
  кредитному счёту.
- `Portfolio.tsx` — 6441 строка, из них ~5700 в одной функции: 98
  `useState`, 50 `useMemo`. Браузерных тестов на портфель почти нет.
- Бот сейчас ничего не присылает пользователю: кода отправки сообщений в
  репозитории нет. Deep link'ам неоткуда взяться.
- В базе 6,3 тыс. операций за 2020–2026 годы. История грузится страницами по
  20 штук при прокрутке.

## Цель

Повторный запуск приложения сразу показывает «Обзор» из прошлого запуска.
Свежие данные подтягиваются в фоне с полосой `RefreshBar`, без сплэша. Первый
запуск (кэша нет) не ждёт искусственные 2 секунды.

**Не входит:** кэш других вкладок (портфель, кредиты, настройки), офлайн-режим
с вводом операций, Telegram CloudStorage, TanStack Query.

План переписан по ревью (раздел «Ревью плана» ниже). Владелец выбрал полный
вариант с кэшем, а не только удаление паузы (п. 19).

## Как устроено

Шаги реализации — отдельные коммиты:

1. **Убрать паузу.** `MIN_SPLASH_MS` и `setTimeout` в `useAuth` удаляются:
   `loading` снимается сразу после ответа контекста.
2. **`ApiError`.** `handleApiResponse` бросает `ApiError extends Error` с
   полем `status`, текст ошибки прежний. Нужно, чтобы отличать 401/403 от
   сети и 5xx (п. 5).
3. **Модуль `frontend/src/startCache.ts`** (около 80 строк, чистые функции,
   без React):
   - одна запись `localStorage['budget_start_cache']`:
     `{ v, identity, savedAt, user, dashboard }`;
   - `cacheIdentity(hasSessionToken, telegramUserId)` — чистая функция:
     `session`, если токен есть (он главнее, как в `apiFetch`), иначе
     `tg:<id>`, иначе `null` (кэш не пишется и не читается);
   - `CACHE_VERSION` — число в коде. Правило в
     `DEVELOPMENT_GUIDELINES.md`: поменял типы, которые лежат в
     `dashboard`, — подними версию. Страховка на случай, если забыли:
     `ErrorBoundary.componentDidCatch` стирает кэш (п. 10). Версию из id
     сборки не берём: деплоев бывает несколько в день, и кэш почти не жил бы;
   - **срок жизни 72 часа**: запись старше не читается. Это мера против
     отключённого устройства и старых цифр без сети (п. 3, решение по
     вопросу 2);
   - `readStart()` — читает запись один раз и проверяет: JSON разбирается,
     `v` совпадает, `identity` совпадает, `0 <= now − savedAt <= 72 ч`
     (запись «из будущего» после перевода часов тоже отбрасывается),
     `user.user_id` — число, `dashboard` — объект. Глубже форму не
     проверяет: от сломанной формы страхует `ErrorBoundary`. Снимок
     остаётся в памяти модуля, `Dashboard` берёт его через
     `startSnapshot()` при монтировании. Возвращает `{ user, ticket } | null`,
     где `ticket = { identity, generation }`;
   - `newTicket()` — тот же билет без чтения, для входа без кэша;
   - `write(ticket, user, dashboard)` — пишет, только если
     `ticket.generation` равен текущему поколению и `ticket.identity` равен
     текущему `cacheIdentity(...)`. `identity` в запись идёт из билета
     (п. 2);
   - `clear()` — удаляет запись, снимок в памяти и увеличивает поколение
     модуля. Поздний ответ, начатый до `clear`, со старым билетом ничего не
     запишет (п. 2). Перемонтированный `Dashboard` после `clear` снимка уже
     не получит (раунд 2, п. 1);
   - цены (`Map` с числовыми ключами) хранятся массивами пар
     `[number, value][]`, при чтении собираются обратно в `Map` (п. 9);
   - любые исключения `localStorage` и `JSON` глотаются: кэш
     необязателен.
4. **Стирание на всех путях смены входа:** `setSessionToken` (вход, выход,
   401 по сессии) вызывает `clear()`; `deleteAccount` в `api.ts` после
   успешного ответа тоже вызывает `clear()`, до `reload` в `Settings` (п. 1).
5. **`useAuth` — единственный читатель** (п. 11):
   - на старте `readStart()`. Есть снимок — `user` из него, `loading = false`,
     контекст запрашивается в фоне;
   - билет для записи берётся **до** отправки `getUserContext`
     (`readStart()` или `newTicket()`), а не в момент ответа. Если `clear()`
     случился, пока контекст был в пути, билет уже устарел и ничего не
     запишет (раунд 2, п. 4);
   - ответ контекста — `user` заменяется свежим, наружу отдаются
     `contextFresh = true` и билет. Другой `user_id`, чем в снимке, —
     сначала `clear()`, потом `newTicket()` для нового пользователя. В `App`
     дерево страниц стоит под `key={user.user_id}`, поэтому `Dashboard`
     перемонтируется без снимка и грузится с нуля, со сплэшем (п. 6);
   - `NoAccountError`, а также `ApiError` 401/403 от `/auth/context` при
     любом способе входа — `clear()`, снимок убирается, дальше прежняя
     логика: вход, выбор аккаунта или экран ошибки (п. 5);
   - сеть и 5xx при показанном снимке — снимок остаётся, `useAuth` отдаёт
     `contextError` и `retryContext()`. `Dashboard` показывает плашку, если
     есть `contextError` или ошибка обзора. «Повторить» вызывает
     `retryContext()`, если контекст ещё не свежий, и `loadOverview`. Пока
     `contextFresh = false`, кэш не пишется (раунд 2, п. 2);
   - без снимка ошибки обрабатываются как сейчас.
6. **`Dashboard`:**
   - начальное состояние — из `startSnapshot()` при монтировании, включая
     цены, `loading = false`; `loadOverview` стартует сразу;
   - **счётчик запросов:** `loadOverview` запоминает номер и по нему
     проверяет весь хвост — применение ответа, `catch` (ошибка и плашка) и
     `finally` (`refreshing`, `loading`). Действует только последний запрос
     (п. 7, раунд 2, п. 5). Так поздний стартовый ответ не перетрёт баланс
     после операции и не снимет `RefreshBar` раньше времени;
   - **эффекты цен** (tinkoff, crypto, moex) и `fetchGroupMembers` зависят от
     флага `fresh` и стартуют только после успешного `loadOverview`, а не от
     данных из кэша. Тогда за запуск идёт одна волна запросов. Ошибка цены
     оставляет прежние значения вместо пустой `Map` (п. 8). Ветки «позиций
     нет → пустая `Map`» не меняются;
   - **запись:** эффект на данные и цены пишет `write(ticket, user, …)`,
     только когда `fresh && contextFresh`. Из `.then` промисов запись не
     делается;
   - **ошибка сети или 5xx при показанных данных** (после кэша или внутри
     сессии: pull-to-refresh, обновление после операции) не подменяет экран
     на `.status-screen`, а показывает плашку (ниже). Это меняет и текущее
     поведение внутри сессии, где сейчас любая ошибка даёт экран ошибки
     (п. 12). Без данных — прежний `.status-screen`;
   - **`ApiError` 401/403 от обзора** — `clear()`, данные скрываются,
     прежний `.status-screen` (как сейчас). Отключённое во время работы
     устройство не должно продолжать показывать суммы (раунд 2, п. 3).

## Дизайн

- **Повторный запуск:** «Обзор» в последнем виде плюс `RefreshBar` до
  ответа. Действия (расход, перевод) доступны сразу: сервер проверяет суммы
  сам, после операции обзор перечитывается, и счётчик запросов не даёт
  старому ответу его перетереть.
- **Обновление не удалось, данные есть:** под шапкой «Обзора» строка
  `role="alert"`, текст `--neg-text`: «Не удалось обновить. Данные от
  4 нояб., 21:40» и кнопка «Повторить» (`.btn`, ghost-вариант). Плашка — и
  для ошибки обзора, и для ошибки контекста (сеть, 5xx). Кнопка нужна
  потому, что на десктопе и в iOS-оболочке нет жеста pull-to-refresh
  (п. 12). Время — последней успешной загрузки: из снимка, потом из
  `loadOverview`. Точный класс выбирает дизайн-сессия, новых токенов нет.
- **Первый запуск, кэша нет, или другой пользователь:** сплэш до ответа, без
  минимальных 2 с.
- **Длинные суммы и названия:** вёрстка «Обзора» не меняется; плашка
  переносит текст на вторую строку, кнопка не сжимается.
- `docs/design-guide.md` §7 «Состояния»: добавить «данные из кэша» и
  «ошибка обновления при показанных данных».
- Проверка на 390px в светлой и тёмной теме, снимок плашки ошибки.

## Критерии приёмки

1. Первый запуск без кэша: в коде старта нет искусственной паузы, «Обзор»
   появляется сразу после ответов контекста и обзора.
2. Повторный запуск с кэшем той же сессии: категории и суммы «Обзора» видны
   до ответа `/auth/context` и `/dashboard/overview`, видна `RefreshBar`.
3. После ответа сервера экран показывает свежие данные, и кэш перезаписан
   ими.
4. Кэш другого `identity` (другой Telegram id, запись `session` без токена),
   старше 72 часов или с `savedAt` в будущем не показывается — путь со
   сплэшем.
5. Выход из аккаунта, вход в другой, 401 по сессии и удаление аккаунта
   стирают кэш.
6. 401/403 или `NoAccountError` от `/auth/context` при показанном снимке
   стирают кэш и убирают снимок с экрана; сеть и 5xx снимок оставляют.
7. Контекст вернул другой `user_id` — снимок прежнего пользователя исчезает
   сразу, кэш стёрт, «Обзор» грузится с нуля.
8. Запрос, начатый до стирания кэша, после стирания ничего не записывает.
9. Поздний ответ раннего `loadOverview` не перетирает данные более позднего
   ни на экране, ни в кэше.
10. За запуск с кэшем каждый запрос цен уходит один раз; ошибка цены не
    обнуляет показанные цены.
11. Битая запись, запись другой версии или запись, на которой падает рендер,
    не ломают запуск: в последнем случае `ErrorBoundary` стирает кэш, и
    повтор идёт без него.
12. Ошибка сети или 5xx (обзора или контекста) при показанных данных
    оставляет данные и показывает плашку `role="alert"` с временем последней
    успешной загрузки и кнопкой «Повторить»; кнопка перезапрашивает контекст
    (если он ещё не свежий) и обзор, после успеха кэш снова пишется. 401/403
    от обзора скрывает данные (`.status-screen`) и стирает кэш. Без данных —
    прежний `.status-screen`.
13. Нет `localStorage` (исключение при доступе) — приложение работает как
    без кэша.

## Откат

Простой revert небезопасен: старый код не знает ключа `budget_start_cache`,
и снимок остался бы в браузере навсегда (п. 18). Откат — revert коммитов
ветки и одним коммитом с ним строка в `main.tsx`:

```ts
try { localStorage.removeItem('budget_start_cache'); } catch { /* ignore */ }
```

Строку держать хотя бы до следующего релиза.

## Известные уязвимости / осознанные риски

- Снимок «Обзора» (балансы, категории, позиции) лежит открытым текстом в
  `localStorage` WebView до 72 часов. Вне Telegram там же уже лежит
  сессионный токен с полным доступом, так что новой поверхности почти нет.
  При входе через Telegram (`initData`) токена нет, и это новое хранение
  данных на устройстве. Шифровать нечем: ключ пришлось бы хранить рядом.
- Привязка записи: к Telegram id, если вход по `initData`; к сессии, если
  есть токен. При email-входе внутри Telegram сессия главнее `initData`
  (`api.ts`), и любой Telegram-аккаунт на этом устройстве увидит снимок
  сессии. Это наследуется от текущего поведения: без кэша тот же человек
  увидит те же данные после загрузки (п. 4).
- **Отключённое устройство.** Отключение сессии из списка устройств или
  смена пароля гасят сессию на сервере, но снимок на том устройстве
  стирается только при его следующем запросе контекста (401). С сетью это
  около секунды, без сети — до 72 часов. Сейчас, без кэша, отключённое
  устройство не показывает ничего (п. 3).
- **Семейные данные.** Снимок содержит семейные категории и счета.
  Пользователь, которого исключили из семьи, видит семейные суммы из снимка
  до ответа сервера, без сети — до 72 часов (раунд 2, п. 7).
- Telegram CloudStorage отвергнут: данные ушли бы на серверы Telegram.

   (`Dashboard.tsx:335`), то есть устройство, отключённое во время работы,
   теряет данные с экрана при следующем обновлении. С планом они остаются.
   `ApiError` со статусом уже вводится: 401/403 от обзора — без плашки,
   экран входа через `useAuth` (или прежний `.status-screen`), данные
   убираются. Добавить в критерий 12 и тест (pull-to-refresh / «Повторить»
   → 401).
4. **исправить** — когда берётся билет. В плане: «ответ контекста — …
   выставляется `contextFresh = true` и билет для записи». Если
   `newTicket()` вызвать в момент ответа, то `clear()`, случившийся пока
   контекст был в пути (401 параллельного запроса обзора по протухшей
   сессии, выход), даст билет нового поколения уже с `identity = tg:<id>`
   для данных аккаунта A, то есть тот же сценарий, что и п. 2 раунда 1.
   Билет берётся **до** отправки `getUserContext` (в каждом `load`, включая
   `refresh`) и используется при ответе. В ветке «другой `user_id`»:
   сначала `clear()`, потом `newTicket()`, иначе новый пользователь до конца
   запуска не запишет кэш.
5. **исправить** — счётчик запросов должен закрывать весь хвост
   `loadOverview`, а не только применение данных: `setError` в `catch` и
   `setLoading`/`setRefreshing` в `finally` (`Dashboard.tsx:166–170`). Иначе
   ранний запрос, завершившийся раньше позднего, снимет `RefreshBar` при
   незавершённом последнем, а его ошибка покажет плашку над свежими данными.
6. **исправить** (мелочь) — срок жизни: запись с `savedAt` в будущем (часы
   устройства переводили) читается как свежая сколь угодно долго. Условие
   чтения: `0 <= now − savedAt <= 72 ч`. Строка в юнит-тест критерия 4.
7. **исправить** (раздел рисков) — к «Отключённому устройству» дописать

   чужие семейные суммы до следующей загрузки, без сети — до 72 часов.
8. **исправить** (тесты) — как написать сценарии:
   - критерий 10: тестовый API без сети, крипто-цены там пустые или с
     ошибкой. Тогда в кэше пустая `Map`, и проверка «502 не меняет сумму»
     проходит и на старом коде (`.catch(() => new Map())`). В первом запуске
     ответ `/crypto/prices` подменить вымышленной ненулевой ценой, во втором
     отдать 502;
   - критерий 1: `page.clock.install()` и `pauseAt` — до `page.goto`. Под

   - задержанные маршруты отпускать через `route.fallback()`, а не
     `route.continue()`, чтобы запрос прошёл через обработчик

   - критерий 5, удаление: принять `window.confirm` (`page.on('dialog')`).
