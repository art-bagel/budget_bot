## Как сократить остаток без потери результата

Согласованное сокращение: S2 использует обычные счета/переводы/награды,
отдельный вид позиции подарков больше не разрабатывается. Повторный разбор
1049 событий, предметный учёт подарков и внутренние операции общего кошелька
не входят в этот проход.

Следующие сокращения согласованы пользователем; исключение — JETTON, для него
автоматическая котировка обязательна:

- **S3:** использовать существующие формы ввода для штрафа,
  добавляя только недостающие поля; возврат комиссии — действие у исходного
  расхода вместо отдельного инструмента. Сохранять связь и фактическую дату.
  Точечный общий признак вместо зависимости от импортера; не переписывать весь журнал.
- **R3.2:** для JETTON найти и подключить автоматическую цену через API,
  проверить контракт/сеть, дату и источник. При сбое не выдавать старую цену за
  текущую. Ручная цена не закрывает требование JETTON; для прочих недоступных
  оценок допустим явный статус неизвестности без отдельного агрегатора цен.
- **S4/R3.3/R5:** один совместный проход по пользовательским сценариям с общим
  протоколом проверки, без трёх повторных полных прогонов одной истории.
- **R4:** одна итоговая выгрузка из финальной dev-базы и краткая сверка вместо
  нового независимого расчёта и серии расходящихся отчётов.

Не сокращать сохранность стоимости/финансирования, защиту от повторного импорта,
сверку банковских операций и резервирование/проверку перед production.
Открытые займы и явно сохранённые неизвестные не требуют бесконечного поиска:
их наличие допустимо в финальном результате согласно границе задачи.

- [ ] **B1. Ручной ввод поступления с неизвестной себестоимостью.** Отложено

  сохраняются; новую форму/механику для неизвестной стоимости сейчас не делать.
  Это исключение касается стоимости поступлений, а не оставшегося учёта штрафов

## Как обновлять этот список

Следующий проход — технические пустые счета и аналитика R3, полный ввод ручных
сценариев S4 (создание пустого счёта уже проверено), затем оставшиеся **R3/S4/R5** совместно → R4 → R6; доступные результаты
для итоговой сводки можно собирать по ходу. Закрытый пункт сопровождается
отчётом/проверкой/коммитом. Составной пункт закрывается частями: импорт через API
не доказывает готовность ручного интерфейса, повтор не доказывает редактирование.
Процент готовности не вычисляем по числу флажков. 27.09 закрыты R1 и R2, результат
применён на dev. Остались согласованность интерфейса, итоговый отчёт, финальная
приёмка и разрешённый перенос в production — R3–R6.
