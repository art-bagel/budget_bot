# Удаление операций вместо пересчёта, даты задним числом — 16.10.2026

Уровень **L**: деньги, SQL-функции журнала, удаление проводок.
Ветка `claude/undo-operations`.

## Цель

Владелец не может исправить ошибку в операции коллекций или крипты:

1. Подарок продан за **26 RUB** вместо **26 GRAM**. На проде это событие журнала
   3197 (`collectible_fiat_close`, предмет 2959, 16.10). Исправить его можно только
   через «пересчёт», а владелец хочет простое удаление и повторный ввод.
2. Продажу нельзя провести задним числом, если позже уже была другая операция:
   «После этой даты уже есть операции. Для изменения прошлого нужен пересчёт».
   А записать продажу в тот же день, когда она случилась, получается не всегда.

Решение — банковская модель:

- **Операцию журнала можно удалить**, если её результат никто не менял позже.
  Иначе сначала удаляются более поздние операции, которые её затронули.
- **Пересчёт истории убирается**: функция `put__correct_crypto_source`, API и
  форма правки количеств. На проде им ни разу не пользовались
  (`crypto_source_corrections` = 0 строк).
- **Дата задним числом разрешается.** У операции две даты:
  - *дата операции* — та, что ввёл пользователь; её видно в истории, по ней
    считаются `operated_on` и `event_at`;
  - *порядок проведения* — операция встаёт в конец журнала.

  Прошлое не пересчитывается, FIFO по монетам идёт в порядке ввода. Ровно так
  уже устроен банковский журнал (`put__journal_bank_operation`, комментарий
  «Bank FIFO follows posting order»).

## Не входит

- Разбор, почему не продаётся B-Day Candle #145397 (позиция 3215) за 20.38. Это
  отдельный шаг после выпуска. Рабочая гипотеза: поле «Сумма продажи» при продаже
  за монеты передаёт строку как есть, и `20,38` с запятой отклоняется Pydantic.
  Ошибка до SQL при этом не доходит. Проверяется отдельно.
- Удаление импортированных событий (`first-hundred-dev-v1`,
  `history-update-2026-09-28`, `bank-legacy-v1`) из интерфейса. SQL их не
  запрещает, но список в UI показывает только ручные источники
  (`manual-portfolio-v1`, `manual-collection-v1`, `bank-posting-v1`).
- Удаление обычных банковских операций вне журнала (доходы, расходы, переводы).
  У них свой механизм.
- Удаление таблиц `crypto_source_revisions` и `crypto_source_corrections`.
  Они остаются как история и сейчас пусты.

## Как устроено сейчас (диагностика)

- Каждая операция крипты и коллекций — событие `crypto_source_events`. Триггер
  `capture__crypto_mutation` пишет в `crypto_source_mutations` каждое изменение
  строк учёта (`before_row` / `after_row`). На проде все 2939 событий помечены
  `reversible = true`.
- Пересчёт `put__correct_crypto_source` откатывает хвост журнала по мутациям в
  обратном порядке, проверяя `actual = after_row`, и проигрывает его заново. Шаг
  отката уже реализован и проверен. Удаление переиспользует его для одного
  события, без повторного проигрывания.
- Запреты «задним числом» стоят в трёх местах:
  - `put__manual_collectible_movement` — по `crypto_source_events.accounting_date`
    и `operations.operated_on`;
  - `put__manual_crypto_movement` — по `portfolio_events.event_at`,
    `accounting_date` и `operations.operated_on` для банковских видов;
  - `put__crypto_source_event` — по `(occurred_at, order_in_timestamp)`.
- Событие 3197 состоит из 7 мутаций, все `INSERT` кроме обновления позиции 2959.
  Откат чистый.

## Решение

### 1. Удаление события — `put__delete_crypto_source(_user_id, _source_event_id, _request_id)`

- Доступ: `has__owner_access` к якорному счёту события; advisory lock журнала
  владельца (`crypto-source:<owner>`). Таблицы учёта блокируются так же, как в
  нынешнем пересчёте (`LOCK … SHARE ROW EXCLUSIVE`, тот же порядок), потому что
  обычные банковские операции не берут lock журнала.
- Повтор с тем же `_request_id` возвращает прежний результат (идемпотентность,
  как у остальных журнальных вызовов).
- Проверка зависимостей — тот же цикл, что в пересчёте. Мутации события
  перебираются в обратном порядке; текущая строка таблицы должна совпадать с
  `after_row`. Не совпала — значит, её изменили позже. Тогда ошибка:
  «Сначала удалите более поздние операции: <дата, вид, название>…». Блокирующие
  события находятся по более поздним мутациям той же строки (`row_key`).
  Изменение вне журнала даёт текст «…изменена операцией вне журнала».
- Порядок действий:
  1. откатить мутации (`DELETE` / `INSERT` / `UPDATE` к `before_row`);
  2. переложить конверт события и его мутации в новую таблицу аудита
     `crypto_source_deletions` (кто, когда, `envelope`, `mutations`);
  3. удалить строки `crypto_source_mutations` и само событие.

  Освобождается `(source_namespace, source_id)`, поэтому та же операция может
  быть введена заново.
- Общие строки-агрегаты (`current_bank_balances`, `current_crypto_balances`)
  делают правило консервативным. После продажи за GRAM нельзя удалить более
  раннюю покупку за GRAM на том же счёте, пока не удалена продажа. Это
  ожидаемо и безопасно.

### 2. Дата задним числом

По образцу `put__journal_bank_operation`:

- `posted := GREATEST(конец выбранного дня UTC, max(occurred_at) владельца)`,
  `order_in_timestamp` — следующий в этой метке;
- выбранная дата идёт в команду как `payload.operated_at`. Диспетчер
  `put__crypto_source_event` передаёт исполнителям
  `COALESCE(payload.operated_at, _accounting_date)`. История уже читает
  `payload.operated_at` первой (`get__crypto_correction_history`);
- проверка конверта `abs(accounting_date - occurred_at) ≤ 1` сохраняется:
  `accounting_date` — дата проведения;
- из `put__manual_collectible_movement` и `put__manual_crypto_movement` убираются
  проверки «после этой даты уже есть операции». Остаются предметные проверки:
  дата продажи не раньше получения предмета, дата не в будущем (если такая
  проверка есть — сверить) и т. п.;
- ключ идемпотентности `evidence` не меняется: в нём уже есть `requested_date`.

### 3. Убрать пересчёт

- SQL: `DROP FUNCTION put__correct_crypto_source`. Из `capture__crypto_mutation`
  удаляется ветка `crypto_replaying` (подмена идентификаторов при
  проигрывании) и `crypto_replay_source` в `put__crypto_source_event`. Флаг
  `crypto_restoring` остаётся: им пользуется удаление.
- API: удалить `POST /crypto/source-events/{id}/correct`, добавить
  `DELETE /crypto/source-events/{id}` (тело: `request_id`).
  `GET /crypto/correction-history` переименовать в `/crypto/source-history` или
  оставить путь — решается при реализации, меньший дифф.
- Фронтенд: `CryptoCorrectionSheet` становится «История операций». Список тот
  же, но в нём все ручные события, а не только с редактируемыми полями.
  Выбранная операция показывает состав и кнопку «Удалить операцию» с
  подтверждением. Форма правки количеств, предпросмотр и токен убираются.

## Критерии приёмки

1. Последнее событие владельца (например, `collectible_fiat_close`) удаляется:
   позиция снова `open` с прежними полями; операция, банковская проводка и
   строка остатка RUB исчезли; остатки и бюджет равны состоянию до события.
2. После удаления та же продажа заново проводится с новой валютой (GRAM) и
   закрывает предмет.
3. Событие, чью строку позже изменило другое событие журнала, не удаляется.
   Ошибка называет блокирующее событие, данные не меняются.
4. Событие, чьи строки позже никто не трогал, удаляется, даже если оно не
   последнее. Пример: покупка предмета A, затем покупка предмета B за другую
   монету на другом счёте — удаляется A.
5. Событие, чью строку изменила операция вне журнала (обычный банковский
   расход), не удаляется: понятная ошибка, данные целы.
6. Удаление чужого события → «Нет доступа», без изменений. Член семьи удаляет
   семейное событие.
7. Повтор удаления с тем же `request_id` возвращает тот же результат без
   ошибки. Новый `request_id` для уже удалённого события → «Операция не найдена».
8. Удалённое событие записано в `crypto_source_deletions` с конвертом и
   мутациями.
9. Продажа предмета с датой раньше последней операции владельца проходит:
   `operations.operated_on` и `portfolio_events.event_at` = выбранная дата,
   событие стоит в конце журнала.
10. Продажа с датой раньше получения предмета по-прежнему отклоняется.
11. Крипто-операция (`swap` / `transfer`) задним числом проходит; FIFO
    списывает лоты в порядке проведения.
12. `put__correct_crypto_source` и `POST …/correct` больше нет. Существующие
    SQL-тесты, которые его вызывали, переписаны на удаление.
13. В интерфейсе: список операций счёта → операция → «Удалить» →
    подтверждение → операция пропала, баланс обновился. Ошибка зависимости
    показана текстом в шторке.

## Известные уязвимости / осознанные риски

- Удаление — прямой откат строк учёта по журналу мутаций. Защита от потери
  данных: строгая проверка `actual = after_row` по каждой строке и аудит в
  `crypto_source_deletions`.
- FIFO по монетам при датах задним числом идёт в порядке ввода, а не по
  фактической дате. Себестоимость монеты может отличаться от «идеального»
  хронологического расчёта. Для подарков разницы нет: у предмета
  индивидуальная себестоимость.

## Ревью плана

Ревьюер: свежая сессия, 16.10.2026. План сверен с кодом ветки на `8398564`.

### Механизм удаления

1. **Исправить.** Проверка `actual = after_row` не ловит ситуацию A→B→A
   (ABA). Событие X записало строку, Y её изменило, Z вернуло ровно прежнее
   значение. X проходит проверку, откат возвращает `before_row` X. Цепочка
   мутаций Y/Z становится неоткатываемой, а Y мог быть возможен только благодаря
   X. У агрегатов балансов ABA закрыт полем `updated_at`
   (`tb/current_crypto_balances.sql:7`). У `crypto_lots`, `fx_lots` и
   `portfolio_positions` такого поля нет (`tb/crypto_lots.sql:3-14`), а ABA там
   реален: правка названия предмета туда и обратно, количество и сумма позиции
   вернулись к прежним. Правило: удалять нельзя, если в `crypto_source_mutations`
   есть более поздняя мутация с тем же `(table_name, row_key)`. Сравнение
   `actual = after_row` оставить только для правок вне журнала. Нужен индекс по
   `(table_name, row_key)`, сейчас есть только по событию
   (`tb/crypto_source_revisions.sql:14`). Тест: ABA на `collectible_details`.
2. **Исправить.** Каскады FK удаляют чужие строки молча. При откате `INSERT`
   позиции выполняется `DELETE portfolio_positions`, а у
   `portfolio_events.position_id` стоит `ON DELETE CASCADE`
   (`tb/portfolio_events.sql:5`). Строка события, которую вставили вне журнала и
   которая не трогает саму позицию, исчезнет без проверки. У
   `operations` (`tb/bank_entries.sql:5`, `tb/crypto_bank_entries.sql:5`,
   `tb/budget_entries.sql:5`, `tb/lot_consumptions.sql:5`) то же самое. Решение:
   на время отката не отключать захват мутаций полностью
   (`func/capture__crypto_mutation.sql:8`), а собирать все изменённые строки во
   временную таблицу. Затем проверять, что их набор совпадает с набором
   `row_key` мутаций события. Иначе — исключение.
3. **Исправить.** Ссылки FK без каскада (`operations.reversal_of_operation_id`,
   `tb/operations.sql:11`; `portfolio_events.linked_operation_id`,
   `tb/portfolio_events.sql:11`; `crypto_lots.opened_by_operation_id`) дают
   сырую ошибку `23503`. Данные целы, но вместо текста владелец увидит
   «foreign key violation». Перехватить `foreign_key_violation` и выдать
   «…изменена операцией вне журнала». Пример: обычный `put__reverse_operation`
   журнальную операцию не запрещает (`func/put__reverse_operation.sql:48-60`),
   поэтому после него банковский расход из журнала дойдёт до этой ошибки.
4. **Исправить.** Повторить предусловия отката из пересчёта:
   `budgeting.crypto_source_event_id = ''` на время отката
   (`func/put__correct_crypto_source.sql:106`). Иначе вставка `before_row` в
   `operations` и `portfolio_events` через `capture__crypto_source_event_link`
   (`func/capture__crypto_source_event_link.sql:7`) создаст лишние ссылки.
   Мутации брать с `revision = событие.revision`
   (`func/put__correct_crypto_source.sql:109-110`). Отказывать, если
   `NOT reversible` или у события нет мутаций, а ссылки в
   `crypto_source_event_links` есть: такое событие удалило бы только конверт.
5. **Исправить.** Перед `DELETE crypto_source_events` нужно разобраться со
   строками в `crypto_source_revisions` и `crypto_source_corrections`: у них FK
   на событие без каскада (`tb/crypto_source_revisions.sql:16,24`). На проде их
   0, но в тестах пересчёта они есть. Переносить их в аудит удаления или
   отказывать с понятным текстом. У `crypto_source_deletions.source_event_id`
   FK на события быть не должно.
6. **Исправить.** Освобождение `(source_namespace, source_id)` опасно. Если
   исходный запрос (тот же `request_id`) запоздало повторится после удаления,
   операция проведётся заново: идемпотентность смотрит только живые события
   (`func/put__manual_collectible_movement.sql:31-36`,
   `func/put__manual_crypto_movement.sql:52-66`,
   `func/put__journal_bank_operation.sql:20-27`). Решение: во всех трёх
   обёртках проверять `crypto_source_deletions` по
   `(owner_key, namespace, source_id)` и выдавать «Операция была удалена».
   Повторный ввод в форме получает новый `request_id`.
7. **Исправить.** Идемпотентность самого удаления: `request_id` должен быть
   UNIQUE в `crypto_source_deletions`. При повторе нужно сверять
   `source_event_id` и `actor_user_id` (как
   `func/put__correct_crypto_source.sql:24-27`) и заново проверять
   `has__owner_access` по `anchor_account_id` из конверта. Иначе чужой
   `request_id` вернёт чужой конверт.
8. **Исправить (безопасность).** Ограничение «только ручные источники» сделать
   в SQL, а не только в UI. `put__delete_crypto_source` отказывает для всех
   namespace, кроме `manual-portfolio-v1`, `manual-collection-v1` и
   `bank-posting-v1`. Импорты откатывать никто не планировал, и тестов на них
   нет.

## Решения по ревью плана (автор)

Все пункты «исправить» принимаются в реализацию. Изменения плана:

- **Правило зависимости (п. 1, 17).** Событие X удаляется, только если ни у
  одной строки из его мутаций нет более поздней мутации другого события
  (`crypto_source_mutations.id > max(id мутаций X)` с тем же
  `(table_name, row_key)`). Блокирующие события перечисляются в тексте ошибки.
  Сравнение `actual = after_row` остаётся как проверка правок вне журнала.
  Добавляется индекс `crypto_source_mutations(table_name, row_key)`.
- **Целостность отката (п. 2–4).** Откат выполняется с
  `crypto_source_event_id=''` и `crypto_restoring='on'`. Мутации берутся по
  текущей `revision`. Отказ, если событие не `reversible` или у него нет
  мутаций. Ошибка FK `23503` перехватывается: «На операцию ссылается более
  поздняя (например, сторно). Сначала удалите её». Каскады проверяются в тесте:
  после отката считается количество строк `portfolio_events` и `bank_entries`
  владельца, и оно должно уменьшиться ровно на число INSERT-мутаций события.
- **Ссылки и аудит (п. 5–7).** Строки `crypto_source_revisions` и
  `crypto_source_corrections` события переносятся в `crypto_source_deletions`
  (jsonb), там FK на события нет. Таблица хранит `request_id` (unique),
  `owner_key`, `source_namespace`, `source_id`, автора и время. Повтор удаления
  сверяет событие и доступ. Чужой `request_id` → «Нет доступа».
  Три ручные обёртки отклоняют повтор запроса, чей
  `(namespace, source_id)` есть в «надгробиях»: «Операция была удалена;
  повторите ввод как новую».
- **Только ручные источники (п. 8)** — проверка в SQL: `manual-portfolio-v1`,
  `manual-collection-v1`, `bank-posting-v1`.
- **Дата операции (п. 10).** Вместо `payload.operated_at` диспетчер берёт дату
  операции из `_evidence->>'requested_date'` для ручных namespace и передаёт её
  исполнителям всех команд события. Белые списки payload не меняются.
  Банковские виды читают дату из payload, как раньше.
- **Проверки дат (п. 11, 12).** Единая проверка в
  `put__manual_collectible_movement` для всех видов с позицией: дата ≥
  `opened_at` предмета и ≥ даты последнего `portfolio_events` предмета. Во
  всех ручных обёртках дата ≤ `current_date + 1` (запас на часовой пояс).
- **История (п. 14).** Сортировка остаётся по порядку проведения: так видно,
  что можно удалить. Если дата операции раньше даты проведения, в строке
  подпись «внесена DD.MM».
- **Документы (п. 15).** План сознательно меняет решение из
  `BUSINESS_LOGIC.md:265-268` и `docs/crypto-accounting-policy.md:491-500`.
  Владелец сам предложил замену пересчёта удалением 16.10.2026. Оба документа
  обновляются в этой ветке.
- **Риск (п. 13)** добавлен: аналитика с фильтром по `event_at` может
  показать промежуточный минус по монете, если продажа внесена задним числом.

## Реализация

Коммиты ветки по шагам:

1. `ec7062f` — SQL.

     (миграция 055 и `tb/`).
   - Банковская модель дат в `put__manual_collectible_movement` и
     `put__manual_crypto_movement`.
   - Диспетчер `put__crypto_source_event` передаёт исполнителям дату операции
     из `evidence.requested_date`.
   - Убраны пересчёт и проигрывание: функция, ветка триггера
     `aa_crypto_identity`, `crypto_replaying` в трёх функциях.
   - «Отменить» у журнальной операции (`put__reverse_operation`) удаляет
     источник.
2. `58471d8` — API: `DELETE /crypto/source-events/{id}?request_id=…`. История
   (`get__crypto_correction_history`, путь `/crypto/correction-history` оставлен)
   показывает все удаляемые ручные источники, дату операции (`accounting_date`)
   и дату проведения (`posted_on`).
3. `8f77590` — фронтенд. Шторка «История операций»:
   - список → операция → «Удалить операцию» → подтверждение в шторке;

   - встроенный список операций пересоздаётся после удаления.

### Что нашли по ходу

- **Дата банковской проводки.** Fiat-функции позиций
  (`put__close_portfolio_position` и соседние) ставили `operations.operated_on`
  по `_operation_at`, по умолчанию «сегодня». Дата операции туда не доходила.
  Раньше это не проявлялось: задним числом проводить было нельзя. Теперь
  диспетчер передаёт `_operation_at => дата операции` для пяти fiat-видов
  коллекций.
- **`crypto.randomUUID`** есть только в secure context и в iOS 15.4+. На
  `http://host.docker.internal` все крипто-формы падали с ошибкой «is not a
  function». В `useCryptoRequestKey` добавлен запасной вариант на
  `getRandomValues`.
- **Метка `updated_at`.** Сравнение `actual = after_row` учитывало
  `updated_at`. Из-за этого после сторно мешающего перевода удаление
  оставалось заблокированным навсегда, хотя остаток уже совпадал. Теперь строки
  сравниваются по значениям без `updated_at`. Строгое правило против
  журнальных изменений (п. 1 ревью: «есть ли более поздняя мутация той же
  строки») не ослаблено.
- **PL/pgSQL не сокращает `AND`.** Обращение к полю неприсвоенной записи в
  условии падает. Правило дописано в `DEVELOPMENT_GUIDELINES.md`.

### Отклонения от плана

- Тесты денежной логики писались вместе с кодом, а не строго до него. Каждый
  критерий закрыт тестом, и тест проверялся на падение при поломке (например,

## Известные уязвимости / осознанные риски (итог)

- Удаление — прямой откат строк учёта по журналу мутаций. Защиты:
  - отказ при любой более поздней журнальной мутации тех же строк;
  - сравнение значений против правок вне журнала;
  - проверка каскадов;
  - аудит в `crypto_source_deletions`.
- Сравнение без `updated_at` означает: правка вне журнала, которая вернула
  значения строки точно к прежним (например, сторно), не блокирует удаление.
  Это осознанно, итог по остаткам при этом верный.
- FIFO монет при дате задним числом идёт в порядке ввода. Аналитика с фильтром
  `event_at <= дата` может показать промежуточный минус по монете, если продажа
  внесена задним числом.
- `deleted_by_user_id` обнуляется при удалении аккаунта: аудит остаётся, автор
  теряется.

### Замечания

1. **Исправить + вопрос владельцу. Регрессия: нельзя отменить обычный расход,
   кроме последнего.** Если у владельца есть хоть одно событие журнала, каждый
   расход с cash-счёта проводится как `bank-posting-v1`
   (`func/put__record_expense.sql:40-44`), а на проде событий 2939. Журнальная ветка
   `func/put__reverse_operation.sql:49-56` превращает «Отменить» в удаление
   источника. Более ранний расход блокирует любая следующая операция по той же
   строке `current_bank_balances` (счёт + валюта) или `current_budget_balances`.
   Блокирует и операция вне журнала, например доход: значения строки
   разойдутся.

   Воспроизведено: покупка монеты → расход 50 → расход 70 → отмена первого
   расхода.
   - `origin/main`: «reverse OK».
   - Ветка: «Сначала удалите более поздние операции…: 16.10.2026 bank_expense».

   То же с операциями `bank-legacy-v1` (импорт старых банковских операций в
   журнал): теперь любая их отмена падает с «Импортированную операцию удалить
