# Ручные обмены и свои переводы через общий журнал

27.09.2026. Продолжение R2, применено только на локальном Docker dev.

## Что теперь может сделать пользователь

Через существующие формы обмена и перевода можно двигать монеты с открытым
заёмным финансированием. Переносятся списанная историческая себестоимость,
качество стоимости и доли заёмных единиц. Рыночная цена для переноса не нужна.
Неизвестная стоимость остаётся неизвестной. Это общий механизм для личных и
доступных семейных счетов; идентификаторов конкретного пользователя в нём нет.

В этих двух формах можно указать дополнительную комиссию в исходной монете.
Основное действие и комиссия проводятся одной транзакцией: при ошибке комиссии
не остаются ни обмен/перевод, ни частично созданный источник. Комиссия в другой
монете поддержана моделью API через отдельную исходную позицию, но выбор другой
монеты в этих формах пока не добавлен.

Полный остаток приходит отдельной десятичной строкой `quantity_exact`.
Формы больше не подставляют количество, округлённое до восьми знаков; ввод
и комиссия передаются строками до 18 знаков. Прежнее числовое поле остаётся
для отображения другими экранами. Это не исправление точности всех DeFi-форм.

## Единая механика и повторы

`put__manual_crypto_movement` вызывает тот же `put__crypto_source_event`, что
и импорт. Обмен всегда использует carry; прежняя переданная рыночная оценка
сохраняется только во входных данных для аудита и не переоценивает монеты.
Заёмные единицы распределяет общий компонентный механизм, проверяющий их
сохранение после каждой команды. Прямые SQL-вызовы с финансированием по-прежнему
защищены: обход журнала не разрешён.

Форма передаёт UUID запроса. Одинаковый повтор возвращает прежний результат,
в том числе после последующих операций и обнуления исходной позиции.
Изменённые данные с тем же ключом отклоняются. Ключ сохраняется в sessionStorage
до подтверждённого успеха, включая повторное открытие формы в той же вкладке.
При недоступном хранилище защита сохраняется в открытой форме. Старые API-клиенты,
не передающие ключ, обслуживаются через журнал, но повтор без ключа является
новым запросом: им необходимо добавить `request_id` для идемпотентности.

Общий owner-lock сериализует ручной журнал с импортом. Форма задаёт дату, а не
точное время: операция добавляется в конец указанного UTC-дня с последовательным
номером. Если после этой даты уже есть криптооперации, ввод отклоняется с
пояснением о необходимом пересчёте. Это безопасный отказ, а не реализация
исторического редактирования. Вставка между событиями одного дня также не является
редактированием: новые ручные действия добавляются последовательно.

## Проверка и применение

`scripts/crypto/test_manual_precision.py`: **12 интеграционных тестов** на
локальной preview, все финансовые записи тестов откатываются:

- финансируемый обмен → комиссия → свой перевод и сохранение стоимости;
- точные количества и заёмные компоненты, контроль общего журнала;
- повтор старого запроса после нового, конфликт данных с тем же ключом;
- ошибка комиссии откатывает все записи (сравнение 17 таблиц);
- чужой владелец, неверная точность/количество и прошлые даты отклоняются;
- новый пользователь без импорта: полный обмен и перевод всего остатка;
- чтение полного остатка строкой через модели API;
- прежние проверки награды, неизвестной стоимости, банковского расхода
  и запрета прямого SQL-обхода журнала.

Frontend typecheck и lint пройдены (160 прежних warnings, 18 infos, без ошибок),
Ruff пройден. В обе dev-базы применены три SQL-функции; отпечатки 17 финансовых
и исходных таблиц до/после совпали. API и web пересобраны из криптоветки и
перезапущены на 8000/8080. Подтверждены поля развёрнутого API и доступность web.
Полный авторизованный визуальный проход остаётся частью R3.3.

Артефакты: `outputs/crypto-manual-movements/` (прежние определения функций,
отпечатки, результаты тестов, сборки и запуска). Production не менялся.
