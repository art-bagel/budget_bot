## Критические

### 1. Токен Тинькофф Инвестиций хранится в БД открытым текстом
**Файлы:** `infra/db/Scripts/budgeting/migrations/018_external_connections.sql`, `infra/db/Scripts/budgeting/func/put__upsert_tinkoff_connection.sql`, `storage/tinkoff.py`

Комментарий в схеме обещает «encrypted token etc.», но токен кладётся в `credentials` (jsonb)
как есть — ни pgcrypto, ни шифрования на уровне приложения нет. Токен даёт доступ к реальному
брокерскому счёту. Дамп/бэкап БД или доступ к ней = утечка токена.

**Исправление:** шифровать токен (pgp_sym_encrypt или шифрование в приложении с ключом из env),
в идеале — хранить только зашифрованным и никогда не отдавать наружу.

---

### 2. Auth-bypass включается молча, если `TELEGRAM_BOT_TOKEN` пуст
**Файлы:** `backend/app/dependencies.py`, `.github/workflows/budget_bot_ci_cd.yml`

Dev-fallback (принять любой `X-Telegram-User-Id` без подписи) активируется, когда токен бота
не задан. В деплое токен приходит из `secrets.TELEGRAM_BOT_TOKEN` — если секрет забыт или пуст,
прод молча открывается для имперсонации любого пользователя. Нет явного признака окружения
(`ENV=production`), который бы запрещал fallback независимо от токена.

**Исправление:** ввести явный флаг окружения; в prod-режиме отказ при пустом токене на старте
приложения (fail fast в `config.py`), а не тихий переход в dev-режим.

---

### 3. Порт Postgres опубликован на хост, дефолтный пароль `postgres`
**Файл:** `infra/docker-compose.yml`

`"${DB_HOST_PORT:-5432}:5432"` — на проде деплой не задаёт `DB_HOST_PORT`, поэтому 5432
торчит на хосте. При отсутствии firewall БД доступна из интернета; дефолты
`POSTGRES_PASSWORD:-postgres` усугубляют риск для любых окружений, где .env не заполнен.

**Статус: осознанно принятый риск (подтверждено владельцем 2026-09-21).**

Порт открыт намеренно: сеть закрыта firewall-ом, снаружи наружу смотрит только Nginx
Proxy Manager. То есть `5432` доступен внутри периметра, а не из интернета, и бинд на
`0.0.0.0` в compose означает «доступен из локальной сети», а не «доступен всем».

Что из этого следует и о чём стоит помнить:

- защита держится на конфигурации firewall, а не на самом приложении. Ошибка в правиле
  или переезд на хост без такого же периметра сразу открывает базу;
- внутри периметра доступ к `5432` не ограничен ничем, кроме пароля Postgres;
- дефолт `POSTGRES_PASSWORD:-postgres` из compose убран — переменная обязательна, без неё
  стек не поднимается.

Если когда-нибудь захочется убрать и этот риск, достаточно одной правки:
`127.0.0.1:${DB_HOST_PORT:-5432}:5432` в `infra/docker-compose.yml`. Ломает это только
подключение к базе с других машин локальной сети (GUI-клиенты, MCP-серверы) — ради чего
порт, судя по всему, и открыт.

### 4. Миграции не применяются при деплое
**Файлы:** `.github/workflows/budget_bot_ci_cd.yml`, `infra/db/init/01-init-budgeting.sh`

Init-скрипты (`run_table_scripts.sh`, `run_func_scripts.sh`) выполняются только при первом
создании тома Postgres. Деплой делает лишь `docker compose up -d --build`. Ни
`migrations/*.sql`, ни обновлённые функции из `func/` на живую БД автоматически не
накатываются — всё вручную (о чём говорит untracked-папка `Scripts/budgeting/manual/`).
Любой релиз, где менялся SQL, рассинхронизирует код API и функции БД, пока кто-то не накатит
руками.

**Исправлено 2026-09-21.** `infra/db/Scripts/run_migrations.sh`: учёт в
`budgeting.schema_migrations` по имени файла, применение одной транзакцией вместе с
отметкой, baseline на первом запуске. Деплой поднимает БД первой, снимает дамп и
накатывает миграции до старта нового API. CI собирает схему с нуля на каждый push.

Побочно вскрылось, что `tb/` разошёлся с миграциями и свежая установка собирала неполную
схему — см. `docs/2026-09-21-migrations-and-ci.md`.

### 5. Любой пользователь может переписать общий справочник крипто-активов
**Файлы:** `backend/app/routers/crypto.py` (`POST /assets`), `infra/db/Scripts/budgeting/func/put__upsert_crypto_asset.sql`

`crypto_assets` — глобальная таблица, а `put__upsert_crypto_asset` при конфликте обновляет
`name`, `decimals` и мержит `metadata` (включая `coingecko_id`, по которому берётся цена).
Один пользователь может «отравить» отображение и цены активов всем остальным: например,
подменить `coingecko_id` у BTC.

**Исправление:** либо сделать активы пер-пользовательскими, либо запретить UPDATE ключевых
полей через публичный эндпоинт (только INSERT новых), либо выделить админский список.

---

### 6. Удаление аккаунта — один запрос без подтверждения
**Файл:** `backend/app/routers/auth.py` (`DELETE /account`)

Необратимое удаление всех данных пользователя одним HTTP-запросом. В сочетании с п.2
(bypass) любой, кто знает user_id, может стереть чужой аккаунт на misconfigured-проде.

**Исправление:** двухшаговое подтверждение (код/задержка/soft-delete с retention).

---

### 6a. Открытие Mini App молча создаёт второй аккаунт и делает привязку невозможной
**Файлы:** `frontend/src/hooks/useAuth.ts`, `backend/app/routers/auth.py`

Найдено 2026-09-20, воспроизведено на дев-стенде.

`useAuth` при наличии Telegram-контекста и отсутствии сессии сразу вызывает `register`.
Для пользователя, который завёл аккаунт по email и потом открыл Mini App, это означает:
под его telegram id молча создаётся **второй, пустой аккаунт**. После этого привязать
Telegram к первому аккаунту уже нельзя — `put__auth_identity` справедливо отказывает
(«Этот способ входа уже привязан к другому аккаунту»), потому что uid занят.

Guard отрабатывает правильно: слить два ledger-а автоматически нельзя. Проблема в том,
что до него дело доходит уже после того, как лишний аккаунт создан. Выхода из этого
состояния у пользователя нет — только удаление второго аккаунта руками.

Этот же автоматический `register` объясняет семь пустых аккаунтов в проде: человек открыл
приложение, аккаунт создался сам, дальше он ничего не сделал.

**Исправлено 2026-09-20.** `/auth/context` для аутентифицированного входа без аккаунта
отвечает 404 (а не 401 — клиент по этому отличает «нужно завести аккаунт» от «вход
невалиден»), фронт показывает выбор: «Создать новый аккаунт» или «У меня уже есть
аккаунт». Вход в существующий из Telegram сразу привязывает этот Telegram к нему.
Регистрация стала явным действием, молчаливого создания аккаунта больше нет.

## Высокий приоритет

### 7. Нет ни одного теста
CI проверяет только `py_compile` трёх файлов и сборку фронта. Вся денежная логика (FIFO-лоты,
реверсы, кредиты, крипто-cost-basis) живёт в 121 plpgsql-функции без единого теста. Для
финансового приложения это главный источник будущих регрессий — особенно при таких частых
правках функций, как сейчас (32 миграции).

**Исправлено 2026-09-21.** CI поднимает postgres:17, собирает схему с нуля и гоняет четыре
SQL-теста плюс сквозной HTTP-тест аутентификации.

Денежная логика покрыта: `money_ledger.sql` (банк и бюджет как независимые слои, расход,
реверс, доступ к чужим ресурсам, сверка проекций с журналом) и `fx_lots.sql` (FIFO,
историческая себестоимость, расход через границу лотов, реверс лота, обмен с FX-результатом).

Тесты проверены мутациями исходных функций — FIFO→LIFO, необновление проекции, потеря
себестоимости при реверсе ловятся все.

**Остаётся непокрытым:** кредиты, крипто-cost-basis, split-доход, переводы между счетами.

**Остаётся главное:** денежной логики это не касается. Инфраструктура для тестов теперь
есть, нужны сами тесты: expense/income, transfer, exchange, reverse, FIFO-потребление,
крипто-свапы.

### 8. `float` для денег по всему стеку
**Файлы:** все Pydantic-модели роутеров, `storage/ledger.py`, фронтенд

Суммы и количества (в т.ч. крипто с 8+ знаками) везде передаются как `float`. Двоичный float
не представляет десятичные дроби точно (0.1 + 0.2 ≠ 0.3); при больших суммах и мелких
крипто-количествах возможна потеря точности ещё до попадания в `numeric`. asyncpg умеет
принимать `Decimal` — сейчас это преимущество не используется.

**Исправление:** `Decimal` в Pydantic-моделях и ledger; на фронте — передавать строки.

---

### 9. Scheduler не защищён от параллельного выполнения и дублей
**Файл:** `backend/app/scheduler.py`

- Несколько инстансов API (или случайный запуск二 контейнера) → двойное исполнение
  scheduled expenses. Advisory lock отсутствует.
- Рестарт между `put__record_expense` и `put__advance_scheduled_expense` → повторное
  списание после старта.

**Исправлено 2026-09-21.** `put__claim_due_scheduled_expenses` читает список и сдвигает
`next_run_at` одной операцией (`UPDATE ... RETURNING` + `FOR UPDATE SKIP LOCKED`). Строка,
попавшая в результат, недоступна для повторного захвата, поэтому advisory lock не
понадобился вовсе. Итог исполнения пишет отдельная функция, которая даты не трогает.

Гарантия изменилась с at-least-once на at-most-once: падение между захватом и записью
пропускает расход, а не дублирует. Для денег это правильная сторона размена.

Закреплено в `tests/scheduled_expenses.sql`.

---

### 10. Цены крипты: публичный CoinGecko без ключа, ошибки глотаются, кэш в памяти
**Файл:** `backend/app/routers/crypto.py`

- Публичный API CoinGecko жёстко лимитирован (~5–15 req/min); 429 ловится как `httpx.HTTPError`
  и молча игнорируется — цены просто пропадают/стареют без логов.
- `_PRICE_CACHE` — процессный dict: пустой после рестарта, неограниченно растёт, не разделяется
  между воркерами.
- `MATIC → matic-network` — устаревший id (мигрировал в POL); цена может перестать приходить.

**Частично исправлено 2026-09-21.** Ошибки CoinGecko больше не глотаются молча —
`logger.warning` с числом запрошенных id и текстом ошибки. 429 теперь виден в логах.

**Остаётся:** `_PRICE_CACHE` по-прежнему процессный dict (пустой после рестарта, растёт без
границ, не разделяется между воркерами), и маппинг `MATIC → matic-network` не проверен на
актуальность после миграции в POL.

### 11. Split-доход: доли ≤ 0 после округления молча пропускаются
**Файл:** `infra/db/Scripts/budgeting/func/put__record_income_split.sql` (строка ~87)

`IF _line_amount <= 0 THEN CONTINUE;` — сумма распределённого может тихо не сойтись
с исходной суммой дохода.

**Исправление:** аккумулировать остаток и добавлять к последней строке; при расхождении —
исключение.

### 12. Секреты и личные данные лежат рядом с репозиторием, .gitignore дырявый

`.gitignore` не покрывает: `node_modules/`, `.idea/`, `.DS_Store`, `*.tsbuildinfo`,

## Средний приоритет

### 13. Накопление копеек при частичном потреблении FX/крипто-лотов

**Разобрано 2026-09-21, деньги не теряются.** Остаток всегда переносится в лот, поэтому
серия частичных списаний сходится точно: 333.33 + 333.34 + 333.33 = ровно 1000.00.
Закреплено тестом в `fx_lots.sql`.

Что действительно верно: пока лот открыт, его себестоимость может отличаться от «идеальной»
пропорции на копейку. На итог это не влияет.

Попутно выяснилось, что формулировка правила в `DEVELOPMENT_GUIDELINES §8` была неверной —
ветка «при полном потреблении брать остаток» ничего не предотвращает, потому что
`cost_base_remaining` это `numeric(20,2)` и обе формулы дают один результат. Формулировка
исправлена там же.

Частичное потребление лота округляется до 2 знаков. Смягчено тем, что при полном потреблении
лота берётся весь `cost_base_remaining` (остаток самокорректируется при закрытии лота),
но пока лот открыт, его cost basis может «гулять» на копейки, и сумма consumed-стоимостей
серии операций не равна пропорциональной доле.

### 14. Нет пагинации и rate limiting
Списковые эндпоинты (`operations history` частично исключение) возвращают всё; лимитов
частоты запросов нет вообще. Для Telegram mini-app с одним пользователем терпимо, при росте —
деградация и уязвимость к флуду.

### 15. `requirements.txt` без версий

**Исправлено 2026-09-21.** Зафиксирован весь набор, включая транзитивные: пиновка только
прямых пакетов не спасает, потому что fastapi допускает диапазон pydantic и starlette, а
ломают обычно они. Версии разрешены под Python 3.10 — ту же ставит `api.Dockerfile` и CI.
`ruff` запинен отдельно в `requirements-dev.txt`.

Расхождение версий Python между локальной машиной и образом остаётся, но теперь CI гоняет
тесты именно на 3.10.

### 16. `config.py` падает с невнятным TypeError при отсутствии env
`int(os.getenv('APP_PORT'))` при незаданной переменной даёт `TypeError: int() argument must
be...` вместо понятного «APP_PORT is not set».

### 17. Пулы соединений: 5 storage-объектов × max_size=5

**Частично исправлено 2026-09-21.** В `lifespan` закрывались три пула из пяти — `auth` и
`tinkoff` утекали при каждом завершении процесса. Теперь закрываются все.

**Остаётся:** пулов по-прежнему пять, до 25 коннектов с инстанса, при этом
`dashboard/overview` параллелит снапшоты через один пул из 5 — при 10+ счетах запросы стоят
в очереди.

### 18. Portfolio.tsx — 5985 строк
God-component: почти вся крипто/портфельная логика фронта в одном файле. Высокая цена любой
правки, высок риск регрессий. `Credits.tsx` (1695) и `Operations.tsx` (1521) идут следом.

### 19. Дублирующиеся номера миграций
`020_drop_legacy_credit_overloads.sql` / `020_investment_asset_type.sql` — пара с одинаковым
номером. Вторая пара (два 019) исчезла 2026-09-21 вместе с удалением
`019_tinkoff_api_debug_dump.sql`.

**Больше не опасно.** Ручного прогона нет: `run_migrations.sh` учитывает миграции по имени
файла, а не по номеру, и применяет их в лексикографическом порядке — то есть детерминированно
и ровно один раз. Дубли номеров остаются косметикой.

### 20. Тексты RAISE EXCEPTION уходят пользователю на английском
`asyncpg.RaiseError` возвращается клиенту как есть (это задумано для user-facing ошибок), но
часть сообщений техническая и англоязычная («Unsupported crypto symbol», «insufficient crypto
balance») при русскоязычном UI.

### 21. TTL initData 24 часа
Окно повтора перехваченного initData — сутки. Для финансового приложения стоит сократить
(Telegram рекомендует валидировать свежесть агрессивнее, например 1–3 часа).

## Порядок исправления

1. **Сейчас:** скоуп `crypto_assets` (п.5) — единственное, что осталось из критических.
2. **Ближайший спринт:** кэш цен в БД и проверка маппинга MATIC/POL (п.10),
   split-остаток (п.11), тесты на кредиты и крипто-cost-basis (продолжение п.7).
3. **Планово:** Decimal вместо float (п.8), коды ошибок вместо подстрок (п.20),
   TTL initData (п.21).
4. **При рефакторинге:** разбор Portfolio.tsx (п.18), пагинация (п.14), пулы (п.17).
