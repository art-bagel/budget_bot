# 2026-09-19 — Аутентификация: способы входа и сессии

## Цель

Отвязать вход в приложение от Telegram, не ломая существующий Mini App.
Это общий фундамент для трёх вещей сразу: нативного iOS-приложения (у него
нет `initData` в принципе), доступности сервиса при блокировке Telegram и
любого будущего способа входа (passkey, Sign in with Apple).

Требование было сформулировано как «сделать сразу нормально, чтобы потом не
переделывать», поэтому выбран не минимальный токен на двоих, а полноценный
слой identity с сессиями.

## Ключевое решение

`users.id` остаётся внутренним идентификатором аккаунта. На нём завязаны все
123 SQL-функции и 77 эндпоинтов, и он не меняется. Способы входа вынесены в
отдельный слой `auth_identities`, где `telegram` и `password` — равноправные
провайдеры, ведущие в один и тот же аккаунт.

Благодаря этому вся бизнес-логика осталась нетронутой: изменения в роутерах
свелись к механическому переименованию `TelegramUser` → `CurrentUser`.

Исторически `users.id` физически равен telegram id, поэтому миграция
существующих пользователей — один `INSERT ... SELECT`.

## Итоговая последовательность действий

1. **Таблицы** (`tb/auth_identities.sql`, `tb/sessions.sql`, правка
   `tb/users.sql`), зарегистрированы в `run_table_scripts.sh` сразу после
   `users.sql`.
2. **Последовательность для локальных id**: `users_local_id_seq` со стартом
   с 2^53. Telegram-id по документации укладываются в 52 бита, поэтому
   коллизия невозможна, а `users.id` получил `DEFAULT nextval(...)`.
3. **SQL-функции**: `get__auth_identity`, `put__auth_identity`,
   `set__auth_login_result`, `put__session`, `get__session_user`,
   `set__revoke_sessions`, `get__user_sessions`, `get__user_auth_methods`,
   `get__user_context`.
4. **`put__register_user_context`** принимает `NULL` вместо `user_id` —
   регистрация без внешнего провайдера берёт id из последовательности.
5. **Миграция 034** — таблицы, последовательность и перенос существующих
   пользователей в `auth_identities` как провайдера `telegram`.
6. **storage**: новый класс `Auth` (`storage/auth.py`), подключён в
   `storage/__init__.py` и `backend/app/storage.py`.
7. **`backend/app/services/passwords.py`** — scrypt из стандартной библиотеки.
8. **`backend/app/dependencies.py`** переписан: `get_auth_principal` разбирает
   любой способ аутентификации, `get_current_user` резолвит его в аккаунт.
9. **`backend/app/routers/auth.py`** — signup, login, logout, context,
   methods, sessions, revoke, password, telegram/link. Старые `register` и
   удаление аккаунта сохранили прежний контракт.
10. **CORS** — добавлен заголовок `Authorization`.
11. **Фронтенд**: `session.ts` (хранение токена), `apiFetch` с
    `Authorization: Bearer` и сбросом токена на 401, `useAuth` с тремя
    состояниями, `components/LoginScreen.tsx`.

### Применение на существующей БД

```bash
cd infra
docker exec budget_bot_db sh -lc 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
    -f /Scripts/budgeting/migrations/034_auth_identities_sessions.sql'
docker exec budget_bot_db sh -lc 'export DB_DATABASE="$POSTGRES_DB"; bash /Scripts/run_func_scripts.sh'
```

Новые переменные окружения:

- `SESSION_TTL_SECONDS` — срок жизни сессии, по умолчанию 90 дней.
- `SIGNUP_INVITE_CODE` — **обязателен**, иначе регистрация по email
  полностью выключена (fail closed).

## Что найдено в процессе

### Гонка при регистрации (исправлена)

Обнаружена при первом же открытии фронта: React StrictMode в dev вызывает
эффект дважды, и оба вызова `put__register_user_context` проходили проверку
«пользователя нет». Функция построена по схеме «прочитать — решить —
вставить» без блокировки, что нарушает правило №1 из
`DEVELOPMENT_GUIDELINES.md`.

Замерено на живом сервере, 6 параллельных регистраций одного пользователя:

| | HTTP-ответы | users | bank_accounts | categories |
|---|---|---|---|---|
| без блокировки | 4×500, 2×200 | 1 | 1 | 2 |
| с `pg_advisory_xact_lock` | 6×200 | 1 | 1 | 2 |

Исправлено одной строкой в начале ветки: блокировка на `_user_id`
сериализует конкурентные регистрации и закрывает сразу все проверки
«прочитать — решить» внутри функции, а не только вставку в `users`.

### `hmac.compare_digest` падает на не-ASCII (исправлено)

Сквозной тест поймал `TypeError` при сравнении кода приглашения, введённого
кириллицей: `compare_digest` на `str` требует ASCII. Сравнение переведено на
байты. Остальные вызовы в проекте сравнивают hex-дайджесты и не затронуты.

### Фреш-инсталл БД неполон (не исправлено, пред-существующее)

`run_table_scripts.sh` не создаёт `external_connections` и колонку
`users.theme` — они появляются только в миграциях, а `migrations/` при
`fresh init` контейнера не прогоняется. На чистой БД `run_func_scripts.sh`
падает на `get__tinkoff_connection.sql`, а регистрация — на отсутствующей
колонке `theme`. Ограничение известно и упомянуто в `README.md`; в рамках
этой задачи не трогалось.

### Сломанный venv проекта (не исправлено)

`venv/bin/python` — висячий симлинк на удалённый `python@3.13` из Homebrew.
`venv/bin/ruff` работает (отдельный бинарник), а запустить питон нельзя.
Проверки прогонялись на отдельном venv в scratchpad. Лечится
`python3 -m venv --clear venv && venv/bin/pip install -r backend/requirements.txt`.

## Проверки

Ни одна из них не требует фреймворков.

| Что | Как запустить |
|---|---|
| Хэширование паролей | `python -m backend.app.services.passwords` |
| SQL-слой | `psql -f infra/db/Scripts/budgeting/tests/auth.sql` |
| API целиком | `python -m backend.tests.test_auth_api` |

Каждый тест проверен мутациями — временной поломкой того, что он должен
ловить. Поймано: снятый guard на привязку чужого входа, снятая проверка
срока сессии, различимые ошибки для неизвестного email и неверного пароля,
снятая блокировка перебора, открытая регистрация, снятая блокировка при
регистрации.

Фронтенд проверен в браузере: вход по токену из `localStorage` поднимает
приложение целиком без Telegram, битый токен вычищается автоматически.

## Известные уязвимости / осознанные риски

1. **Регистрация по email закрыта одним общим кодом приглашения.** Код не
   одноразовый, не истекает и не привязан к адресу. Для двух пользователей
   приемлемо; при появлении третьего нужны одноразовые приглашения. Пока
   `SIGNUP_INVITE_CODE` не задан, регистрация выключена целиком — это
   намеренный fail closed.

2. **Пароль не восстанавливается.** Нет ни подтверждения email, ни сброса
   пароля. Забытый пароль сейчас лечится только правкой в базе. Подтверждение
   адреса нужно до того, как пользователей станет больше двух.

3. **Сессия живёт 90 дней и продлевается скользящим окном.** Компромисс в
   пользу удобства: нативный клиент не должен просить пароль каждую неделю.
   Отзыв возможен, но UI для него ещё не написан (см. п. 5).

4. **`session_id` в API — это hex от sha256 токена.** Знание хэша не даёт
   войти, а эндпоинт доступен только владельцу, но отдельный суррогатный
   ключ был бы аккуратнее. Сделано так, чтобы не заводить лишнюю колонку.

5. ~~**Экрана «Входы и устройства» нет.**~~ Закрыто 2026-09-20:
   `frontend/src/components/SecuritySection.tsx` на вкладке «Аккаунт» —
   список сессий с пометкой текущей, отзыв чужих, выход, управление
   способами входа.

6. **Блокировка перебора — на способ входа, а не на IP.** Пять неудач
   блокируют конкретный email на 15 минут. Это защищает пароль, но позволяет
   намеренно заблокировать вход известному пользователю. Для двух
   пользователей приемлемо.

7. **Dev-фоллбэк `X-Telegram-User-Id` сохранён.** Работает только когда не
   задан `TELEGRAM_BOT_TOKEN` и `APP_ENV` не `production`, как и раньше.

## Открытые вопросы

- Восстановление забытого пароля: нужен backend подтверждения email.
- Одноразовые коды приглашения вместо одного общего — до третьего
  пользователя не критично.
- Место хранения токена в нативной обёртке — Keychain вместо `localStorage`;
  менять надо только `frontend/src/session.ts`.
