## Исправление производительности

`put__correct_crypto_source` раньше для каждой восстановленной строки искал
совпадение JSON по всей таблице. Теперь используются типизированные первичные
ключи и индексы. У временной очереди прежних идентификаторов добавлены индексы
для поиска незадействованной записи и её отметки. Проверка полного совпадения
текущей строки с записанным состоянием после операции сохранена.

20 интеграционных сценариев прошли за 19,502 секунды. Оптимизация применена
к `budget_bot` и `crypto_merge_preview`; все 19 таблиц каждой базы неизменны.
Код интерфейса и API в этом проходе не менялся, пересборка контейнеров не нужна.

Полный просмотр истории остаётся тяжёлой транзакцией с блокировкой учётных
таблиц. Его нельзя считать мгновенным пользовательским действием или доказанной
готовностью параллельного production. При переносе учитывать измеренные шесть
минут; сохранность данных важнее снятия блокировок без эквивалентной защиты.

## Почему импортированные исправления ещё не включены

Видимый dev не заменён восстановленной копией. После импорта существуют:

1. 12 распределений оплат карты, расход выручки от друга и 3 сентябрьские
   банковские операции — **16 завершающих операций** вне источников истории.
2. Отдельное распределение между категориями, операция **22321**, на
   **2 083 534,52 RUB**, выполненное уже после импорта. Его нет в исходном бэкапе;
   слепая замена базы потеряла бы это распределение.
3. Поздние пояснения о неподтверждённых начислениях в metadata семи DeFi-позиций.

Идентификаторы самих 1960 источников и связанных проводок совпали. Идентификаторы
повторной финализации отличаются: PostgreSQL sequences продвинулись во время
пробных пересчётов, даже после отката. Поэтому финализацию нельзя копировать
поверх текущих строк. Нужно сохранить её существующие идентификаторы и категории
при подключении к пересчёту, а времена созданных снимков сопоставить с исходными
транзакциями. Добавленная текущим кодом метка `basis_policy=journal` у шести
событий конвертации стейкинга также должна быть явно учтена при переносе снимков.
Финансовые количества/стоимости этих конвертаций не изменились.

Это остаток прежних R2.2.c/d, а не новый разбор блокчейна. Восстановление снимков
и полный тест preview выполнены; публикация снимков с сохранением служебных
полей и пересчёт внешних банковских операций ещё не выполнены. **На видимом dev
у старых 1960 источников остаётся `reversible=false`**. Безопасный отказ сохранён.

## Чистая PostgreSQL 17

Создана отдельная пустая `crypto_schema_acceptance`. Проверены все файлы таблиц
в штатном порядке и все функции с приоритетным списком сборщика. Столбцы,
типы, точности, nullable/default и индексы совпали с обновлённым dev.
Ограничения эквивалентны: различаются представление приведения массива varchar
к text и автоматически назначенные имена трёх CHECK у журнала обязательств;
набор выражений ограничений по таблицам одинаков. Свежая установка не требует
ручного добавления криптообъектов. Это закрывает R5.1, но не финальную приёмку R5.2.

## Воспроизведение и артефакты

Из корня криптоветки, с зависимостями проекта и локальным Docker:

1. `scripts/crypto/rebuild_history_snapshots.py --prepare` — создаёт только новую
   `crypto_revision_preview`; существующую базу не перезаписывает.
2. `--replay` — полный либо возобновляемый прогон с проверкой затрат.
3. `--verify-sources` — сравнение источников с видимым dev.
4. `--test-correction` — полный откатываемый preview; запускать **до** финализации.
5. `--finish` — повтор сохранённых банковских категорий и поздних операций.
6. `scripts/crypto/verify_crypto_clean_schema.py` — независимая проверка схемы.

Все команды запускаются Python окружения проекта с `PYTHONPATH=.:scripts/crypto`.
Ни одна не подключается к production. Существующую проверочную базу не удалять
для повторения: использовать сохранённые результаты либо отдельно подготовить
явно изолированный прогон. Обычный `--replay` не создаёт дубли.

Закрытые артефакты: `outputs/crypto-history-revisions/`: план и состояние полного
прогона, `source-proof.json`, `early-correction-preview.json`, контрольные суммы,
`final-verification.json`, сравнение конечных строк, `clean-schema.json`, тесты,
`deployed.json`, дампы обеих dev-баз до оптимизации и `reconstructed-history.dump`.
Дампы и личные данные не добавлены в git. Для отката только оптимизации достаточно
вернуть прежнее определение функции из `152c970`; финансовые записи не менялись.
